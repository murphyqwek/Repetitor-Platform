# Assignment Service — требования и бизнес-правила

**Дата:** 27 ноября 2026 года  
**Статус:** актуальная редакция после согласования БД и API. Раздел 13 фиксирует последующие решения, делегированные технические defaults и внешние блокеры. Транспортные детали — в отдельных REST/Kafka-контрактах.  
**Проект:** платформа для онлайн-занятий репетиторов.

## 1. Назначение и границы сервиса

Assignment Service отвечает за банк математических задач, их импорт и версии, конструктор домашних работ и пробных экзаменов, назначение работ, индивидуальное выполнение, автоматическую и ручную проверку, самостоятельные тренировки, статистику успеваемости и формирование событий уведомлений.

В рамках текущего проектирования это один микросервис с функциональными модулями, а не отдельные микросервисы для банка, экзаменов, проверки, парсинга и аналитики.

Смежные компоненты:

- **Identity Service** — пользователи, роли, блокировки, связи родителя и ребёнка; источник истины для этих данных.
- **Education Service** — курсы (курс и группа являются одной сущностью), их владельцы, текущие зачисления, библиотека преподавателя и реестр внешних ссылок на материалы.
- **PostgreSQL** — собственная БД Assignment. Идентификаторы внешних сущностей хранятся без межсервисных SQL FK.
- **MinIO** — приватное объектное хранилище изображений условий и файлов решений.
- **Kafka** — события через Transactional Outbox; доставка писем и иных уведомлений относится к будущему Notification Service.

Технологический ориентир существующего проекта: Java, Spring Boot, Gradle Kotlin DSL, PostgreSQL, Kafka, MinIO. Конкретные версии и настройки сверяются с репозиторием на этапе реализации.

## 2. Банк заданий

### 2.1. Источники и видимость

- Поддерживаются общедоступные импортированные задачи и приватные задачи, созданные преподавателем вручную.
- Импортированные задачи доступны всем преподавателям и ученикам (самостоятельная сдача ограничена разделом 8).
- Приватная задача доступна преподавателю-владельцу, администратору и ученикам, которым выдана работа с этой задачей, в рамках соответствующего назначения. Она не появляется в общедоступном банке ученика.
- Другие преподаватели не могут выбирать чужие приватные задачи в свои работы.
- Администратор видит, редактирует и удаляет существующие задачи с учётом ограничений, но не создаёт собственные задачи вручную.
- Преподаватель вправе скопировать импортированную задачу в приватный банк. Копия имеет собственный постоянный идентификатор и независимую историю версий; изменение копии не изменяет оригинал.

### 2.2. Содержимое задачи

Задача имеет условие, формат ответа, данные для проверки, максимальный балл по умолчанию, учебные темы, при необходимости экзаменационную классификацию, изображения и необязательное пояснение правильного решения. Для импортированной задачи сохраняется информация об источнике и внешнем идентификаторе; для приватной — преподаватель-владелец.

- Условия и пояснения поддерживают Markdown и математические формулы LaTeX.
- Изображения могут быть размещены внутри условия; объекты хранятся в приватном MinIO.
- Для автоматической проверки задаются правильные ответы, для задач с выбором — варианты ответа, для соответствий — позиции и ожидаемые значения.
- Правильные ответы и пояснения не выдаются ученику до наступления разрешённого момента. Учитель и администратор видят данные для проверки в рамках своих прав.
- Точные DTO, безопасный рендеринг Markdown, проверка файлов и ограничения размеров условий будут определены при проектировании API и реализации.

### 2.3. Форматы и способы проверки

| Формат | Проверка | Правило |
|---|---|---|
| `TEXT` | Автоматическая | Нормализация и сравнение с допустимыми строками |
| `NUMBER` | Автоматическая | Числовое сравнение без ошибок двоичной плавающей точки |
| `SINGLE_CHOICE` | Автоматическая | Сравнение выбранного идентификатора варианта |
| `MULTIPLE_CHOICE` | Автоматическая | Сравнение множеств выбранных идентификаторов, порядок не важен |
| `MATCHING` | Автоматическая | Сравнение соответствий по каждому ключу |
| `FILES` | Ручная | Преподаватель проверяет прикреплённое решение |

Для `MATCHING` преподаватель определяет позиции (например A, B, C) и значения; ученик вводит значение для каждой позиции. Иллюстративный формат ответа: `{"A":"1","B":"2","C":"3"}`. Окончательная схема ответа будет задана в API.

Для чисел допустимы десятичная запятая и точка, внешние пробелы, эквивалентные десятичные представления (`2,5`, `2.5`, `2,50`); `5/2` не считается эквивалентной записью. Полноценный математический парсер не реализуется. Для текстовых и иных применимых форматов разрешено несколько допустимых правильных ответов. Детали нормализации текста и значений соответствий фиксируются отдельно.

К автоматическим задачам ученик может прикрепить фотографии хода решения (необязательно); это не превращает автоматическую проверку в обязательную ручную проверку.

### 2.4. Баллы

- Баллы только целочисленные; по умолчанию автоматически проверяемая задача имеет максимум 1 балл. Для ручной проверки задаётся максимальный балл по умолчанию.
- Автоматическая проверка начисляет 0 или весь максимальный балл. Частичные автоматические баллы не начисляются, в том числе для `MULTIPLE_CHOICE` и `MATCHING`.
- Ручная проверка допускает целое значение от 0 до максимума включительно.
- В обычном конструкторе преподаватель может переопределить максимальный балл конкретной позиции работы, не меняя задачу банка. Для строгого экзаменационного варианта действуют ограничения раздела 7.
- Преподаватель может вручную изменить результат автоматической проверки; исходный автоматический балл сохраняется отдельно.

### 2.5. Версии, редактирование и удаление

- Задача имеет постоянный ID. Каждое изменение содержимого создаёт новую неизменяемую версию; старые домашние работы и попытки тренировок продолжают ссылаться на прежнюю версию.
- Содержимое версии включает условие, изображения, ответы, формат проверки, пояснение, баллы и классификацию, необходимые для воспроизведения старой работы. Неизменившиеся физические объекты MinIO не требуется копировать.
- При удалении задачи, на которую ссылается домашняя работа, она логически удаляется: исчезает из банка и недоступна для нового выбора, но сохраняется для исторических ссылок и уже выданных работ.
- Восстановление удалённых задач не поддерживается. Парсер также не восстанавливает удалённые администратором задачи.
- Нельзя физически удалять данные, необходимые для истории работ или самостоятельных решений.
- Неиспользуемые задачи физически удаляются асинхронно, использованные в шаблоне/назначении/тренировке скрываются. Для импортированной сохраняется tombstone. Шаблон с удалённой задачей нельзя публиковать до замены.

## 3. Справочники и классификация

- Поддерживаются математика ОГЭ, базовая математика ЕГЭ и профильная математика ЕГЭ. Другие предметы пока не входят в область реализации.
- Экзамен, год и номер позиции в структуре экзамена отделены от математической темы.
- Импортированная задача обязательно классифицируется по экзамену, году и позиции. Администратор управляет справочником экзаменационных структур и тем, в том числе соответствиями позиции темам.
- Задача может относиться к нескольким темам. Преподаватель указывает темы своих задач; администратор может уточнять классификацию импортированных задач.
- Для обычной авторской задачи экзаменационная классификация необязательна; это не мешает использовать задачи для школьников, не готовящихся к экзамену. Для включения в строгий экзаменационный вариант соответствующая классификация необходима.
- Версия задачи может относиться к нескольким позициям различных экзаменов/лет (N:M). Структуры экзаменов и шкалы версионируются.

## 4. Конструктор и назначение домашних работ

### 4.1. Разделение сущностей

Различаем три понятия:

1. **Шаблон работы** — сохраняемый преподавателем набор задач, порядок, баллы и название. Может быть сохранён без публикации, редактироваться и переиспользоваться.
2. **Назначение** — конкретная выдача шаблона с зафиксированным содержимым, настройками, дедлайном, комментарием и получателями.
3. **Индивидуальная работа** — выполнение конкретного назначения одним учеником, со своими ответами, файлами, состоянием и результатами проверки.

Один шаблон можно назначать разным ученикам и курсам. Одному ученику один и тот же шаблон повторно не назначается. Изменение шаблона не меняет уже опубликованные назначения.

### 4.2. Получатели

- Преподаватель может выбрать одного или нескольких учеников, один или несколько своих курсов либо сочетание курсов и отдельных учеников.
- Отдельно выбранный ученик должен состоять хотя бы в одном курсе этого преподавателя.
- При назначении курсу получателями становятся ученики, состоящие в нём на момент публикации. Состав получателей фиксируется; при пересечении курсов и отдельных списков ученик получает одну индивидуальную работу.
- Новое зачисление не приводит к автоматической выдаче ранее опубликованных домашних работ.
- Добавление новых получателей к опубликованному назначению запрещено.
- Отзыв у конкретного ученика разрешён до отправки на проверку. Персональные дополнения к групповому составу не поддерживаются; для индивидуальной работы создаётся отдельное назначение.
- Повторное назначение того же шаблона одному ученику запрещено, включая отозванные работы и изменённые шаблоны с тем же ID.

### 4.3. Редактирование и удаление

| Операция | Шаблон / до публикации | Опубликованное назначение |
|---|---|---|
| Название, комментарий | Можно менять | Можно менять |
| Дедлайн | Можно задать | Можно изменить до его истечения |
| Добавление/удаление задач | Можно | Нельзя |
| Порядок задач | Можно | Нельзя |
| Максимальные баллы | Можно в пределах режима | Нельзя |
| Замена версии задачи | Можно | Нельзя |
| Добавление получателей | При подготовке | Нельзя |

Неопубликованный шаблон можно удалить. Использованный шаблон можно скрыть, сохраняя необходимые исторические данные. Опубликованное назначение без отправленных работ можно отменить; назначение с отправленными работами нельзя физически уничтожать, допускается скрытие/архивирование с сохранением истории. Архив скрывает назначение из активного списка учителя; ученик сохраняет историю и право закончить активную попытку. Отмена отзывается только для незавершённых неистёкших работ; физического удаления опубликованного назначения нет.

### 4.4. Настройки назначения

- Название, комментарий преподавателя, обязательный дедлайн, список получателей.
- Режим `HOMEWORK` или `EXAM`; длительность обязательна для режима `EXAM`.
- Одна попытка.
- Политика показа правильных ответов: `NEVER`, `AFTER_SUBMISSION`, `AFTER_DEADLINE`, `AFTER_REVIEW`.
- Default `AFTER_DEADLINE`; пояснения и правильные решения используют ту же политику. Политика неизменяема после публикации. Для AFTER_DEADLINE нужны сдача и истечение общего дедлайна.
- До окончания попытки правильные ответы не раскрываются через интерфейс конкретной работы. Автоматические баллы видны после сдачи независимо от политики показа правильных ответов.

## 5. Выполнение работы и файлы решений

### 5.1. Статусы индивидуальной работы

| Статус | Значение |
|---|---|
| `NOT_STARTED` | Назначено, ученик не приступил |
| `IN_PROGRESS` | Выполнение, сохранение ответов |
| `SUBMITTED` | Отправлено, автоматическая проверка выполнена, ожидается ручная проверка |
| `IN_REVIEW` | Преподаватель сохраняет промежуточные результаты |
| `REVIEWED` | Итоговый результат опубликован |
| `MISSED` | Дедлайн истёк без сохранённых ответов/файлов |
| `REVOKED` | Работа отозвана до сдачи |

Основной переход: `NOT_STARTED → IN_PROGRESS → SUBMITTED → IN_REVIEW → REVIEWED`. Полностью автоматически проверяемая работа после сдачи сразу получает `REVIEWED`, без обязательного подтверждения преподавателем. Отзыв и истечение времени обрабатываются отдельно. После сдачи обратного перехода к редактированию ответов нет.

### 5.2. Черновик и отправка

- Ученик сохраняет, меняет и очищает отдельные ответы до отправки и до истечения разрешённого времени. Frontend может использовать автосохранение с debounce.
- Черновик хранится на сервере и доступен при повторном открытии с другого устройства. Автосохранение не запускает проверку и не раскрывает правильность ответа.
- Допускается сдавать частично выполненную работу. Перед окончательной отправкой frontend запрашивает подтверждение.
- Ученик явно отправляет работу кнопкой; система фиксирует ответы и выполняет автопроверку. После этого ответы и прикреплённые файлы нельзя редактировать.
- При истечении дедлайна сохранённые ответы автоматически отправляются на проверку. Если ни одного сохранённого ответа или прикреплённого файла нет, применяем `MISSED`. Явная пустая сдача начатой работы допустима (делегированное техническое решение).
- **Истёкший дедлайн не продлевается.** Это окончательное уточнение заменяет более раннее разрешение продления после истечения. Нет возврата автоматически сданной работы ученику, восстановления попыток или отката проверки.
- Сервер контролирует время. Запись после окончания времени запрещена, даже если фоновый обработчик ещё не завершил работу. При гонке между сохранением, сдачей, отзывом, изменением дедлайна и фоновой отправкой не допускаются изменения уже зафиксированных ответов и двойная сдача.

### 5.3. Вложения решений

| Ограничение | Значение |
|---|---:|
| Разрешённые форматы | JPG, JPEG, PNG, WEBP, PDF |
| Один файл | 20 000 000 байт |
| Число файлов на задачу | 10 |
| Суммарно на задачу | 50 000 000 байт |
| Суммарно на индивидуальную работу | 200 000 000 байт |
| TTL непривязанных файлов | 24 часа |

1 МБ = 1 000 000 байт. Сохранённые решения хранятся, пока существует работа и требуется история.

- Загрузка через backend Assignment в приватный MinIO; бинарные данные не передаются через Kafka. Выдача файла — только после проверки полномочий на backend.
- Файл предварительно загружается, получает ID, затем привязывается к ответу. Владелец, контекст работы/задачи, готовность, размер, тип и совокупные лимиты проверяются сервером.
- До отправки можно удалять и заменять файлы; после отправки изменение запрещено.
- Непривязанные файлы очищаются фоновым обработчиком. Удаление объектов идемпотентно, с повторными попытками; необходимо учитывать гонки с незавершёнными загрузками.
- Сбой загрузки не делает файл доступным как успешно сохранённый. При повторе не должно возникать потерянных объектов.

## 6. Проверка и оценивание

### 6.1. Автоматическая проверка

- Выполняется синхронно при сдаче (в том числе при фоновой сдаче по времени). Отдельная очередь вычислений не требуется.
- Проверяем по версии задачи, закреплённой в назначении, и по максимальному баллу этой позиции.
- Сохраняем исходный автоматический балл, ручной балл/переопределение при наличии и итоговый балл; итог вычисляется с учётом переопределения. Способ физического хранения вычисляемого результата определим в БД.
- Нерешённые задачи получают 0 баллов при окончательном оценивании; ручные задачи с решением ожидают проверки.
- Полностью автоматическая работа публикует итог без участия преподавателя; он сохраняет право изменить результат позднее.

### 6.2. Ручная проверка

- Преподаватель видит очередь своих сданных работ, ответы и файлы решений; может проверять задачи в произвольном порядке.
- Допускаются комментарии к отдельной задаче и общий комментарий к работе.
- Можно сохранять черновик проверки и вернуться к нему позднее.
- Преподаватель может выставить балл любой задаче, в том числе переопределить автоматический результат.
- Завершение проверки — отдельное явное действие. Перед публикацией должны быть определены все необходимые баллы.
- До публикации ученик видит только исходные автоматические баллы; промежуточные ручные оценки, переопределения и комментарии скрыты.
- После публикации ученик видит окончательные оценки и комментарии, а правильные ответы — согласно политике назначения. Создаётся событие о завершении проверки.
- Возврат на доработку не поддерживается.

### 6.3. Изменение опубликованной оценки

Преподаватель может исправить баллы и комментарии уже проверенной работы. Итоговый результат и аналитика должны обновиться; публикуется событие `SubmissionGradeUpdated`. Полноценную историю изменения ручных оценок не ведём, храним актуальный результат и первоначальные автоматические баллы. Правила атомарной публикации исправлений будут определены в API.

### 6.4. Очередь и история

Преподавателю доступны ожидающие проверки, находящиеся в процессе проверки, проверенные и все работы. Предусматриваем фильтрацию по ученику, курсу, шаблону, статусу, дате назначения и дедлайну, пагинацию. Очередь ожидающих проверки сортируется от наиболее давно отправленных работ к новым. Исторические работы сохраняются после исключения ученика и удаления курса.

## 7. Пробные экзамены и варианты

### 7.1. Единая модель

Экзамен не является отдельной моделью индивидуального выполнения: используем общие назначения, ответы, статусы, проверку и историю. Экзаменационный вариант как набор задач может назначаться как обычная домашняя работа (`HOMEWORK`) или как экзамен (`EXAM`).

| Параметр | HOMEWORK | EXAM |
|---|---|---|
| Общий дедлайн | Обязателен | Обязателен |
| Индивидуальный таймер | Нет | Есть |
| Черновики, выход и повторное открытие | Да | Да, в пределах таймера |
| Попытки | Одна | Одна |
| Автоматическая сдача по дедлайну | Да | Да |
| Автоматическая сдача по таймеру | Нет | Да |

### 7.2. Конструктор экзаменационного варианта

- Администратор задаёт структуру экзамена по виду экзамена и году: позиции, максимальные баллы и стандартную длительность.
- Преподаватель может подобрать задачи вручную либо сгенерировать случайный вариант автоматически и затем заменить отдельные позиции.
- Для каждой позиции выбираются задачи соответствующей экзаменационной классификации. Допускаются собственные задачи преподавателя с нужной классификацией.
- Количество и порядок позиций, максимальные баллы соответствуют структуре экзамена. Переопределять максимальный балл позиции строгого экзаменационного варианта нельзя.
- Неполный вариант можно сохранить как черновик, но нельзя публиковать. При недостатке задач генерация должна сообщить о незаполненных позициях.
- Варианты переиспользуются как шаблоны, с общим запретом повторного назначения одному ученику. Состав опубликованного варианта неизменяем.
- Для нестандартного набора задач и произвольных баллов используется обычный конструктор ДЗ.

### 7.3. Таймер

- Таймер начинается только после явного действия «Начать экзамен». Простое открытие карточки не начинает попытку.
- Сервер фиксирует `startedAt`. Длительность берётся из настроек назначения; преподаватель может изменить стандартную длительность при назначении.
- Время завершения: `endAt = min(startedAt + duration, deadline)`.
- Если до общего дедлайна меньше времени, чем длительность экзамена, перед стартом показываем предупреждение.
- Паузы, сброс таймера, повторный старт и прокторинг не поддерживаются. Закрытие страницы, смена устройства или системного времени клиента таймер не останавливают.
- По истечении времени сохранённые ответы отправляются на проверку. Запись ответа за пределами времени запрещена самим backend, независимо от задержки worker.
- Результаты проверки не показываются в течение попытки; после отправки действуют общие правила отображения автоматических баллов, ручной проверки, ответов и пояснений.
- При переносе неистёкшего общего дедлайна пересчитываем effectiveDeadline для ещё активных попыток по исходному startedAt; не продлеваем собственную длительность экзамена и не открываем истёкшие попытки.

### 7.4. Экзаменационные шкалы

- Сохраняем первичные баллы (сумму оценок позиций) и результат преобразования.
- Профильный ЕГЭ — тестовые баллы; базовый ЕГЭ и ОГЭ — оценка. Конкретные официальные шкалы в данном документе не задаются.
- Администратор управляет шкалами по виду экзамена и году. Шкалы версионируются; опубликованный вариант сохраняет ссылку на конкретную версию.
- Перевод баллов реализуется отдельным классом/компонентом, например `ExamScoreConverter`. Предложенная реализация — универсальный конвертер, получающий версию шкалы из БД, без отдельного Java-класса на каждый год.
- Итоговый преобразованный результат показываем после окончательной проверки; при исправлении опубликованных баллов результат пересчитывается по той же версии шкалы.
- Валидация шкал должна учитывать полноту диапазона, непротиворечивость и специальные правила конкретного экзамена, если они необходимы. Нельзя подставлять условную шкалу вместо утверждённой.

## 8. Самостоятельные тренировки

- Для самостоятельной сдачи доступны только активные общедоступные импортированные задачи с автоматической проверкой. Ручные задачи не отправляются учеником на проверку в режиме тренировки.
- Фильтры по экзамену, году, номеру позиции, темам, решённости и результату предыдущего решения.
- **Одна самостоятельная попытка на задачу.** Ранее предложенные неограниченные попытки отменены. Повторно решать неправильно решённую задачу в этом режиме нельзя; фильтр позволяет найти её в истории, а не сдать ещё раз.
- После отправки ответа система сразу проверяет его, сохраняет результат, показывает правильный ответ и пояснение при наличии.
- Нет отдельного черновика, дедлайна или очереди ручной проверки.
- История выполненных задач и ответов сохраняется; результат привязан к конкретной версии задачи.
- Уникальность самостоятельной сдачи по `(studentId, taskId)`, независимо от версии. Назначенные работы не блокируются наличием самостоятельной попытки. Повтор идентичного запроса возвращает сохранённый результат; иной ответ запрещён.

## 9. Аналитика и автоматический подбор

### 9.1. Исходные данные

Учитываем результаты домашних работ, пробных экзаменов и самостоятельных тренировок; предусмотрена фильтрация по типу работы. Черновики и промежуточная ручная проверка не включаются в итоговую статистику. Исправление опубликованной оценки обновляет статистику. История сохраняется за весь период.

### 9.2. Оценка тем

Для оценённой задачи вычисляем нормализованный результат `r_i = score_i / maxScore_i`, для темы — среднее арифметическое соответствующих нормализованных результатов `R = sum(r_i) / n`.

- Для определения текущих слабых тем используются последние 30 дней.
- Если в теме менее 5 различных решённых задач — недостаточно данных.
- При достаточных данных: менее 50% — слабая тема, от 50% до менее 80% — требует практики, от 80% — освоена.
- Динамика и общая статистика доступны за выбранный период; полная история сохраняется.
- Пороговая оценка — согласованная простая статистическая эвристика, не ML-модель и не доказанная педагогическая диагностика.
- Каждая оценённая позиция REVIEWED (включая нулевые пропуски) и самостоятельная попытка участвуют в среднем; повторы taskId в разных работах дают отдельные наблюдения, но COUNT DISTINCT по taskId. MISSED/REVOKED исключены. Дата результата — submittedAt; maxScore положителен.

### 9.3. Подбор по слабым темам

Преподаватель выбирает ученика, экзамен, год и число задач. Система получает слабые темы, сортирует по возрастанию успеваемости, выбирает подходящие доступные задачи с приоритетом ранее не решённых и исключает дубликаты. Возвращает предлагаемый состав, который преподаватель может изменить. Автоматической публикации нет. При недостатке данных/задач система сообщает об этом; квоты пропорциональны слабости, приоритет не назначавшихся и не решённых задач, при нехватке допустимы ранее решавшиеся. Частичный результат с предупреждением, без случайного подбора при отсутствии слабых тем.

### 9.4. Доступ

| Роль | Доступ к аналитике |
|---|---|
| Ученик | Только собственная |
| Преподаватель | Общая статистика учеников, состоящих хотя бы в одном его курсе |
| Администратор | Все ученики |
| Родитель | Нет |

Преподаватель не получает через аналитику условия, ответы и комментарии чужих приватных домашних работ. После исключения ученика из всех курсов данного преподавателя общая аналитика недоступна ему, но ранее выданные им работы и результаты сохраняются.

## 10. Импорт и парсер заданий

### 10.1. Архитектура и управление

- Парсер — модуль Assignment Service. Интерфейс адаптера источника (например `SourceParser`) отделяет получение и преобразование данных от общей логики импорта, валидации и сохранения.
- Первый предполагаемый источник — РЕШУ ЕГЭ. Другие источники подключаются разработчиком, не произвольным кодом из административного интерфейса.
- Администратор настраивает поддерживаемые категории (вид экзамена, год, позиции), включение/отключение источника, расписание, запускает импорт вручную, просматривает состояние и журнал операций.
- Конкретный допустимый механизм получения данных, условия использования источника и права на копирование заданий, изображений и решений ещё не проверены. Реальный импорт зависит от этой проверки. Документ не утверждает наличие официального API или разрешения массового копирования.

### 10.2. Идентичность и обновление

Идентифицируем импортированную задачу по источнику и внешнему идентификатору. Пространство идентификаторов источника необходимо уточнить (если различные экзаменационные разделы используют пересекающиеся ID, включить раздел в идентичность).

| Ситуация | Действие |
|---|---|
| Новая задача | Создаём задачу и первую версию |
| Содержимое не изменилось | Пропускаем |
| Изменилось условие, ответ, изображение или иные значимые данные версии | Создаём новую версию |
| Задача исчезла из источника | Не удаляем локальную задачу автоматически |
| Задача удалена администратором | Не восстанавливаем автоматически |
| Администратор вручную изменил задачу | Парсер не перезаписывает ручное исправление |

Для выявления изменений используем хеш нормализованного содержимого. Администратор может снять запрет на автоматическое обновление. Старые версии и ссылки сохраняются.

### 10.3. Изображения и классификация

При наличии необходимых прав изображения загружаются в собственный приватный MinIO; условие и формулы приводятся к Markdown + LaTeX, внешние ссылки на изображения заменяются внутренними идентификаторами. Не публикуем частично импортированную задачу, если обязательные изображения отсутствуют.

Импортированные задачи получают экзаменационную классификацию. Темы назначаются по соответствию экзаменационной позиции и года справочнику тем; администратор может вручную уточнить темы конкретной задачи. ИИ для классификации не используется.

### 10.4. Асинхронность и ошибки

- Импорт запускается асинхронно. Одновременно допускается один активный импорт на источник.
- Состояние запуска, счётчики, ошибки и итоговый статус сохраняются в PostgreSQL.
- Каждая задача обрабатывается отдельной атомарной логической операцией, а не в общей транзакции на весь импорт. Ошибка одной задачи не откатывает успешно импортированные остальные.
- Внешние запросы используют таймауты, ограничение частоты и повторные попытки с backoff.
- Повторный запуск после сбоя или рестарта не создаёт дубликаты задач и версий. Необходима долговечная защита от параллельных запусков и зависших операций.
- Журнал показывает число добавленных, обновлённых, пропущенных задач и ошибки. При завершении с ошибками публикуется `TaskImportFailed` для уведомления администратора.
- Массовый JSON-импорт собственных задач преподавателем присутствовал в первоначальных сценариях, но предложение отложить его не было явно подтверждено. Он не входит в согласованный объём текущей реализации до отдельного решения.

## 11. Уведомления и межсервисные события

### 11.1. События Kafka

| Событие | Причина | Получатель будущего уведомления |
|---|---|---|
| `AssignmentPublished` | Назначена новая работа | Ученик |
| `AssignmentDeadlineChanged` | Изменён дедлайн | Ученик |
| `AssignmentDeadlineReminder` | Наступил срок напоминания | Ученик |
| `AssignmentRevoked` | Отозвана работа | Ученик |
| `SubmissionReceived` | Работа поступила на ручную проверку | Преподаватель |
| `SubmissionReviewed` | Итог проверки опубликован, в том числе автоматически | Ученик |
| `SubmissionGradeUpdated` | Изменена опубликованная оценка | Ученик |
| `TaskImportFailed` | Импорт завершился с ошибками | Администратор |

**Родителям уведомления не отправляем.** Assignment не реализует отправку писем, Telegram или иные каналы доставки. Ответственность Assignment — события; ответственность будущего Notification Service — непосредственная доставка.

Бизнес-изменение и запись в Transactional Outbox сохраняются в одной локальной транзакции PostgreSQL. Kafka недоступна — уже выполненная бизнес-операция не откатывается, событие остаётся в outbox до повторной публикации. Доставка at-least-once; потребитель дедуплицирует по стабильному ID события. Topic, partition key, версии схем, payload и правила порядка определены в assignment_service_kafka_contract.md.

### 11.2. Напоминания

- За 72 часа, 24 часа и 1 час до дедлайна.
- Запланированные напоминания хранятся в PostgreSQL и обрабатываются фоновым worker.
- Только для ещё не сданных и не отозванных работ; оставшиеся напоминания после сдачи/отзыва отменяются.
- При изменении дедлайна время напоминаний пересчитывается. Истёкший дедлайн не продлевается.
- Если на момент назначения интервал уже прошёл, соответствующее напоминание пропускается.
- После сбоя не отправляем лавину устаревших напоминаний; при восстановлении отправляем максимум последнее актуальное напоминание, остальные пропускаем.
- Повтор worker не создаёт второе логическое уведомление. Событие формируется в одной транзакции с отметкой об обработке напоминания.
- Между формированием события и реальной доставкой состояние работы может измениться; правила подавления уже опубликованных, но устаревших уведомлений будут согласованы при проектировании Notification Service.

| Создание приватных задач | Да | Нет | Нет | Нет |

| Просмотр приватных задач | Свои | Только выданные | Все | Нет в MVP |
| Создание шаблонов и назначение | В пределах своих курсов/учеников | Нет | Управление существующими; создание за учителя не входит в MVP | Нет |

Роль администратора не отменяет ограничения сохранности истории, дедлайна, баллов, неизменяемости опубликованного состава или использования файлов. Просмотр родителем самих домашних работ/результатов не согласован (старый UC-PA-03 предполагал просмотр ДЗ); в текущем MVP не предоставляем отдельный parent-only доступ.

### 12.2. Исключение ученика и удаление курса

- При исключении из курса ранее выданные работы не отзываются автоматически: ученик может выполнить и сдать их, преподаватель — проверить, завершённые результаты сохраняются.
- Новое назначение через курс без актуального членства невозможно. Если ученик по-прежнему состоит в другом курсе преподавателя, отдельное назначение допустимо в соответствии с общими правилами.
- При удалении курса все назначения, индивидуальные работы, решения, результаты, ссылки на версии задач и нужные файлы остаются в Assignment. Удаление курса не блокирует завершение ранее выданного ДЗ.
- Храним идентификаторы выбранных курсов и снимки их названий на момент назначения, чтобы история оставалась понятной после удаления курса. При нескольких курсах требуется хранить соответствующий набор связей.
- Существующий Education Service по-прежнему самостоятельно очищает расписание, чат, членства и права доступа курса к библиотеке; не требуется каскадно удалять Assignment-данные.
- Преподаватель сохраняет право на собственные исторические работы даже без текущего членства ученика; доступ к общей аналитике определяется актуальным членством.

### 12.3. Блокировка

Identity Service — источник истины о пользователях и блокировке. Заблокированный пользователь не может пользоваться Assignment, включая просмотр, выполнение, проверку (если это преподаватель), тренировки, выдачу файлов и аналитику. Его данные не удаляются. Дедлайны и таймеры не приостанавливаются, фоновая отправка выполняется. Незаблокированный преподаватель может проверить работу заблокированного ученика; администратор управляет сохранёнными объектами. После разблокировки доступ возвращается по актуальным статусам без восстановления истёкших попыток.

### 12.4. Файлы Education Service

Разделение ответственности:

| Категория | Владелец данных |
|---|---|
| Изображения условий задач и пояснений | Assignment / MinIO |
| Фото и файлы решений | Assignment / MinIO |
| Файлы из библиотеки преподавателя | Education / MinIO |

- При использовании учебного файла в версии задачи регистрируем ссылку в реестре `material_reference` Education. Идентификатор потребителя относится к версии задачи, а не только к постоянному taskId.
- Пока хоть одна сохраняемая версия использует файл, удалять его нельзя (включая удаление содержащей его папки). Администратор не обходит запрет.
- Отвязка файла в новой версии не освобождает ссылки старых версий. Освобождение возможно только когда соответствующая ссылка действительно перестала быть необходимой.
- Файл не копируется в Assignment. Доступ ученика к нему проверяется по контексту назначенной работы и версии задачи, независимо от ACL библиотеки. Перемещение файла, исключение из курса и удаление курса не прекращают такой доступ к сохранённой работе.
- Education уже имеет внутренние маршруты регистрации и освобождения ссылок (`POST /internal/v1/materials/{fileId}/references`, `DELETE /internal/v1/materials/{fileId}/references/{referenceId}`). Для выдачи через контекст Assignment потребуется согласовать внутренний контракт чтения, аутентификацию сервиса и подтверждение ссылки. Нельзя использовать регистрацию ссылки как единственную проверку права конечного пользователя.
- Регистрацию ссылок, публикацию версии и компенсацию частичного сбоя требуется спроектировать как надёжную межсервисную операцию с идемпотентностью, без долгой SQL-транзакции на время сетевых вызовов. Версия, требующая файл, не должна становиться доступной, пока нужная ссылка не подтверждена. Точный алгоритм будет задан в DB/API-проекте.

### 12.5. Недоступность зависимостей

| Операция | Зависимость недоступна | Поведение |
|---|---|---|
| Новое назначение / проверка состава курса | Education | 503, если нельзя достоверно подтвердить права и получателей |
| Проверка блокировки / полномочий | Identity | 503 при отсутствии достоверной актуальной информации; fail closed |
| Регистрация или чтение библиотечного материала | Education | Ошибка зависимости, операция не считается успешно выполненной |
| Публикация события | Kafka | Outbox и повторная доставка |
| Загрузка файла решения | MinIO | Ошибка загрузки с возможностью повторить |
| Сохранение текстового ответа | Kafka / MinIO | Не зависит от них при отсутствии файловых операций и при успешной авторизации |

Для уже назначенной работы актуальный состав курса не нужен как условие доступа. Межсервисные проверки должны быть защищены, не доверять внешним идентификаторам от клиента без валидации. Проверяем Identity синхронно без Redis-кэша, для внутренних вызовов — короткоживущие служебные JWT. Конкретный механизм выпуска и внешнего JWT/cookie/CSRF сверяем с фактическим кодом Identity и Education.

## 13. Итоговые решения после проектирования БД и API

**Согласовано пользователем:** все блоки БД, публичного REST, внутренних API и Kafka. Технические детали из соответствующих контрактов обязательны. В частности:

- 36 таблиц; без school_grade/difficulty, grading_criterion/criterion_grade, workspace, отдельных получателей и аналитических агрегатов. JSONB для ответов. Неиспользуемые задачи удаляются физически; использованные сохраняются. Нельзя публиковать шаблон с удалённой задачей. Версии в шаблоне меняются вручную.
- Одна submission на получателя и постоянный запрет повторного назначения одного шаблона даже после отзыва; явный skipAlreadyAssigned/skipBlockedStudents, атомарная публикация, Idempotency-Key. Архив сохраняет активные попытки. Политика reveal неизменна после публикации.
- Ответы создаются лениво, сохраняются с revision; отдельный start, экзамен до старта без условий, поздняя загрузка отклоняется. Конкуренция READ COMMITTED + locks, общая reviewRevision, явный ноль ручной задачи, атомарное исправление опубликованных оценок, без истории прежних оценок.
- Тренировка по taskId, история версий, version conflict без расхода; аналитика по дате сдачи, UTC-группировка; подбор пропорционален слабости. Не блокировать импортированную задачу в тренировке из-за назначения.
- Импорт с конфигурациями и job history, cron UTC, REST polling, retry новым запуском, без повторного импорта удалённых задач. Источник не может перезаписать ручную правку. Все восемь событий Assignment через один topic assignment.events.v1, outbox at-least-once. Нет родительских уведомлений. Identity batch, Education snapshot/membership, Saga ссылок, service JWT, fail closed, без реплики и circuit breaker в MVP.

### 13.1. Делегированные технические решения для реализации

Пользователь попросил самостоятельно завершить спецификации/тесты/план. Следующие defaults выбраны при сведении документов, а не являются отдельными прямыми ответами пользователя:

| Вопрос | Решение редакции |
|---|---|
| Родительский просмотр самих ДЗ | Не включать отдельный parent-only доступ до утверждения; аналитика и уведомления явно запрещены. |
| Создание администратором за преподавателя | Не включать; админ управляет существующими объектами; при генерации чужого шаблона используется банк его владельца. |
| JSON-импорт преподавателя | Не включать, поскольку не был явно согласован. |
| Пустая сдача и отзыв | Явная пустая сдача начатой работы допустима; по времени без сохранённых ответов/файлов MISSED. При отмене сначала учитывать уже истёкшие попытки, MISSED сохранять, не возобновлять. |
| Материалы | MaterialIds — материалы условия; registration checks owner/actor. Для позднего POST после compensation — durable release tombstone в Education; status route для pending версии. |
| Напоминания | 72/24/1h от общего дедлайна, suppress после effective cutoff; новая deadlineRevision на каждый перенос, при downtime максимум последнее актуальное. |
| Kafka | aggregateSequence, сохранённый в агрегате; publisher не обгоняет раннее неопубликованное событие; consumer обязан дедуплицировать. |
| Идемпотентность | Сохранённый исходный receipt (а не актуальные изменяемые поля назначения) и hash request; долговечные keys. |
| Импорт после crash | Потерянный lease завершает запуск FAILED/INTERRUPTED; retry новым job со старым snapshot, не удваивать counters; missed cron не навёрстывать. |
| Загрузка файлов | Уникальный object key, upload state/lease и периодический reconciliation orphan objects; не полагаться только на TTL. |
| Валидация и аналитика | Лимиты и JSON по REST, даты сдачи, все оценённые позиции в AVG, distinct по taskId, тема N:M, пустое значение null; нет выдачи чужих ID работ. |

### 13.2. Внешние блокеры перед реализацией

- Наличие нужных provider endpoints и фактическая модель JWT/cookie/CSRF, способ service JWT. Проверить код, не угадывать. Нужны минимальные дополнения в Education/Identity; чужие БД не читаем.
- Разрешённость массового получения и хранения материалов РЕШУ ЕГЭ, реальные форматы и external ID namespace. Без этого только тестовый адаптер/fixtures, production source выключен. Не подменять официальные экзаменационные структуры/шкалы демонстрационными данными; специальные условия перевода требуют проверки и возможного расширения.
- Notification Service остаётся за границей MVP; схема Kafka подготовлена, фактическая доставка уведомлений не реализуется Assignment.

## 14. Инженерные требования к реализации

Модель PostgreSQL, REST DTO, внутренние API, Kafka, тест-план и пошаговая реализация находятся в этом же комплекте. Приоритет имеют текущие документы и решения раздела 13.

При проектировании БД и тестов обязательно обеспечить:

- неизменяемость опубликованного состава и версии задачи, сохранность результатов после изменений банка;
- уникальность получателя в назначении, отсутствие повторной сдачи и дубликатов при конкурентных запросах;
- корректное серверное ограничение времени и атомарность переходов состояния;
- недоступность промежуточных ручных оценок и чужих приватных задач;
- согласованность лимитов файлов при конкурентных загрузках, отсутствие потерянных объектов MinIO;
- идемпотентный импорт и невозможность перезаписи ручных исправлений;
- сохранение истории при удалении курса и исключении ученика;
- надёжную регистрацию ссылок Education, outbox, фоновые задачи и восстановление после частичных отказов;
- тесты на позитивные и негативные сценарии, конкуренцию и внешние сбои с реальными PostgreSQL/MinIO/Kafka там, где это необходимо.
