# Education Service — контракт истории чата курса

**Статус:** согласованный REST-контракт истории чата MVP (20.11.2026).  
**Область:** чтение истории чата и вложений. Отправка через WebSocket/STOMP, ACK после коммита, дедупликация по `clientMessageId` и REST catch-up согласованы; точные минимальные STOMP destinations/JSON-события закреплены в `chat_websocket_contract.md`.

## Принятые ограничения

- Каждый курс имеет собственный чат.
- История доступна владельцу курса, администратору и текущему ученику курса; ученик видит всю историю независимо от даты зачисления.
- Исключённый ученик доступа не имеет. Запрет отправки сообщений не запрещает чтение.
- Сообщения в состоянии `DELETING` и окончательно удалённые сообщения не возвращаются; заглушки об удалении нет.
- Поддерживаются текст до 4000 символов и изображения/файлы JPG/JPEG/PNG/WEBP/PDF/DOCX/XLSX/TXT; не более 5 вложений общим размером до **50 000 000 байт**, максимум **20 000 000 байт** на файл (1 МБ = 1 000 000 байт); временные вложения хранятся 24 часа.
- Редактирование и ответы на сообщения (reply) не предусмотрены.
- Вложения отдаются через backend Education Service, без публичных ссылок MinIO.

## GET /api/v1/courses/{courseId}/chat/messages

**Назначение:** получить страницу истории чата курса.

**Авторизация:** `Authorization: Bearer <token>`.

**Query:**

| Имя | Тип | Обязателен | Значение |
| --- | --- | --- | --- |
| `limit` | integer | Нет | По умолчанию `50`; допустимо `1..100` |
| `before` | opaque string | Нет | Получить сообщения старше указанной позиции. Без него — последние сообщения |

Пример:

```http
GET /api/v1/courses/86b6ceef-50b3-4ab0-8997-1304129ebc61/chat/messages?limit=50
Authorization: Bearer <access_token>
```

**Успех:** `200 OK`, `Content-Type: application/json`.

```json
{
  "messages": [
    {
      "id": "b7c3e8e2-9a51-4db7-904a-19b7a824f541",
      "author": {
        "id": "7f4d2d9a-27d4-47a2-b91d-3be3a61d21e7",
        "displayName": "Иван Иванов",
        "role": "STUDENT"
      },
      "text": "Здравствуйте! Вот моя работа.",
      "createdAt": "2026-11-20T12:30:00Z",
      "attachments": [
        {
          "id": "5f328b4c-6766-426b-87ef-5fdd824d1e34",
          "fileName": "solution.png",
          "contentType": "image/png",
          "sizeBytes": 3145728,
          "kind": "IMAGE",
          "downloadUrl": "/api/v1/courses/86b6ceef-50b3-4ab0-8997-1304129ebc61/chat/messages/b7c3e8e2-9a51-4db7-904a-19b7a824f541/attachments/5f328b4c-6766-426b-87ef-5fdd824d1e34/content"
        }
      ]
    }
  ],
  "nextCursor": "opaque_cursor_value",
  "hasMore": true
}
```

### Поля

- `messages`: сообщения **от новых к старым**.
- `id`: уникальный UUID сообщения.
- `author.id`: UUID пользователя из Identity Service.
- `author.displayName`: **снимок имени на момент отправки**, из `chat_message.author_display_name`; изменение имени пользователя в Identity не переписывает старые сообщения.
- `author.role`: роль в контексте сообщения (`STUDENT`, `TEACHER`, `ADMIN`).
- `text`: `string | null`; сообщение может состоять только из вложений.
- `createdAt`: серверная дата/время создания, ISO 8601 UTC.
- `attachments`: массив, при отсутствии вложений `[]`.
- `attachments[*].kind`: `IMAGE` либо `FILE`; `contentType` соответствует сохранённому MIME.
- `downloadUrl`: backend URL, требующий авторизации и проверок доступа; объектный ключ MinIO не раскрывается.
- `hasMore`: имеются ли более старые сообщения.
- `nextCursor`: позиция для следующего запроса `before`; `null`, когда `hasMore=false`.

### Правила выборки

1. Проверить аутентификацию и доступ: владелец курса, администратор или текущий участник-ученик.
2. Убедиться, что курс доступен, и исключить сообщения в состоянии `DELETING`.
3. Выполнить keyset pagination по `(created_at DESC, id DESC)`. Курсор должен быть непрозрачным, привязанным к курсу и пригодным даже после физического удаления опорного сообщения.
4. Запрашивать из БД `limit + 1` запись, чтобы вычислить `hasMore`.
5. Возвращать не более `limit` сообщений; курсор следующей страницы формировать из последнего возвращённого сообщения.

Пример условия БД (после безопасного декодирования курсора):

```sql
SELECT id, course_id, author_id, text, created_at
FROM chat_message
WHERE course_id = :course_id
  AND state = 'ACTIVE'
  AND (
       :cursor_created_at IS NULL
       OR (created_at, id) < (:cursor_created_at, :cursor_id)
  )
ORDER BY created_at DESC, id DESC
LIMIT :limit_plus_one;
```

Рекомендуемый индекс:

```sql
CREATE INDEX idx_chat_message_course_created
ON chat_message (course_id, created_at DESC, id DESC)
WHERE state = 'ACTIVE';
```

`id` служит детерминированным вторым ключом при совпадении временных меток. При удалении и появлении новых сообщений курсорная пагинация не сдвигается, в отличие от OFFSET; однако это не «снимок» истории на момент первого запроса.

### Ошибки

| Статус | Причина |
| --- | --- |
| `400 Bad Request` | Неверный `limit`, повреждённый, неподходящий или просроченный курсор |
| `401 Unauthorized` | Нет корректной аутентификации |
| `403 Forbidden` | Пользователь не имеет доступа к чату (не является текущим учеником, владельцем или администратором) |
| `404 Not Found` | Курс отсутствует или недоступен как удаляемый |

Для ошибок можно использовать единый `application/problem+json` (RFC 9457), как и в других API платформы.

## GET /api/v1/courses/{courseId}/chat/messages/{messageId}/attachments/{attachmentId}/content

**Назначение:** скачать/получить изображение или файл из истории чата.

- Требуется тот же уровень авторизации на чтение чата, что и для истории.
- Дополнительно проверяются принадлежность вложения сообщению/курсу и состояние сообщения `ACTIVE`.
- При состоянии `DELETING` вложение больше не доступно; при отсутствии ресурса — `404`.
- Файл потоково читается Education Service из приватного MinIO и отдаётся клиенту; публичного адреса MinIO нет.
- Рекомендуемые заголовки: корректный `Content-Type`, `Content-Disposition`, `X-Content-Type-Options: nosniff`, приватное управление кэшированием.

## Клиентские правила

1. При входе в чат запросить первую страницу истории.
2. Добавить сообщения на экран в хронологическом порядке (сервер возвращает страницу в обратном порядке).
3. По прокрутке вверх передавать `before=nextCursor`, пока `hasMore=true`.
4. Новые сообщения получать через WebSocket; объединять с историей по уникальному `id`, чтобы избежать дубликатов.
5. При получении WebSocket-события удаления убрать сообщение из локального списка; сервер всё равно запрещает доступ к нему и вложениям.
6. **При переподключении WebSocket переподписаться, очистить старый локальный список и перечитать актуальную историю через REST**. Не дополнять старый кэш только последними 50 сообщениями — так можно пропустить старые удаления. Дальние страницы загружать заново при прокрутке; события, пришедшие во время REST-перезагрузки, временно буферизовать и применить после ответа. Отдельный `chat_event`/sequence catch-up **не используется**.

## Принятый контракт и технические детали реализации

- REST route, авторизация, DTO и курсорная пагинация выше приняты как **базовый контракт MVP**. При повторном подключении к WebSocket клиент заменяет локальную историю актуальной первой страницей REST, а старые страницы при необходимости перечитывает; **журнал `chat_event` не используется**.
- STOMP destinations, `MESSAGE_CREATED`, `MESSAGE_DELETED`, `MESSAGE_ACCEPTED` и `MESSAGE_REJECTED` уже заданы в `chat_websocket_contract.md`. Это отдельный согласованный документ, не открытый пункт.
- Точные меры защиты предпросмотра и проверки MIME (при неизменном whitelist), устройство курсора и оптимизация запросов — техническая реализация. `chat_send_receipt` для дедупликации хранится до удаления курса, без TTL.
- Публичный `GET` статуса cleanup-задач в MVP **не вводим**; скрытие сообщения/вложений происходит на backend сразу после перехода в `DELETING`.

## Связанные решения

- Удаление курса **реализуется сейчас**; только судьба связанных домашних заданий/решений определяется позже в Assignment Service.
- Для ACL отдельного файла принят простой приоритет явного правила файла над наследованием от папки; при перемещении файл наследует права нового размещения, если нет собственного правила.
- Нужны Kafka-события об отмене отдельного занятия и остановке регулярного расписания.
- Администратор вправе отправлять сообщения **включая режим `ANNOUNCEMENTS`**; ученики в этом режиме только читают.
- Остановка регулярного расписания относится к **исходной дате вхождения**; переносы с более ранней исходной датой сохраняются.
- Создающие `POST` курсов и занятий не требуют `Idempotency-Key` в MVP; для отправки чата используется `clientMessageId`.
