# Education Service — пошаговый план реализации для Codex

**Версия:** 20.11.2026  
**Назначение:** исполняемое ТЗ для AI coding agent (Codex), а не обзор архитектуры.  
**Стек проекта:** Java 17, Spring Boot 4.1.1, Gradle Kotlin DSL, PostgreSQL 17, Kafka, приватное S3-совместимое хранилище MinIO. Существующая локальная инфраструктура находится в `docker/local`; менять чужие сервисы без необходимости нельзя.  
**Область:** Education Service платформы репетиторов: курсы/участники, расписание, библиотека материалов, чат курса, фоновые удаления и Kafka-outbox.  
**Источники истины:** пять согласованных документов, приложенных к задаче; настоящий документ описывает *порядок реализации*, но не заменяет требования.

## 0. Как Codex должен использовать этот документ

### 0.1. Неподвижные ограничения

1. **Перед изменениями прочитать все пять документов:**
   - `education_service_requirements_latest.md`;
   - `education_service_db_design.md`;
   - `education_service_rest_api_contract.md`;
   - `chat_history_api_contract.md`;
   - `chat_websocket_contract.md`.
   Если на диске имена содержат `(1)`, использовать фактически существующие файлы и не создавать дубликаты с иной спецификацией. **Если источников нет в рабочем дереве Codex — сначала попросить их предоставить / поместить в `docs/education/`, не выдумывать контракт по этому плану.**
2. Сначала изучить репозиторий и принятый стиль Identity Service: Java/Gradle, конфигурация JWT, Docker Compose, структуры пакетов, тесты. **Не копировать чужой код без проверки** и не рефакторить Identity/Assignment попутно.
3. Реализовывать **ровно один этап за запуск**, если пользователь не задал другой диапазон. Подзадачи внутри этапа выполнять полностью, включая миграции, обработку ошибок и тесты. Не начинать следующий этап автоматически.
4. Не изменять контракты API, данные и бизнес-решения ради удобства реализации. Если обнаружено противоречие или необходим новый межсервисный контракт — зафиксировать проблему, предложить минимальное решение и остановить **только затронутую подзадачу**; остальную работу этапа продолжить.
5. Не оставлять `TODO` или заглушку там, где критерий этапа обещает готовое поведение. Если тест нельзя выполнить, указать *точную* причину и команду воспроизведения; не писать «всё проверено» без запуска.
6. Данные пользователей из Identity — внешние UUID, **не SQL FK** в Education. Запросы от имени пользователя определяются JWT, а не `teacherId`/`authorId` в теле запроса; исключение — явно согласованный административный маршрут.
7. Не делать прямые публичные ссылки к MinIO, presigned-URL для браузера, прямую загрузку браузера в хранилище или бинарные сообщения STOMP. Вся загрузка/выдача файлов идёт через backend.
8. Не делать отдельный `chat`-микросервис, таблицу `chat_event`, бессрочные записи физических занятий для повторяющейся серии, публичный `GET /cleanup-jobs/{id}`, поддержку редактирования сообщений/ответов на них и автоматическую интеграцию Телемоста.
9. **Удаление курса входит в эту реализацию.** Не откладывать его до Assignment Service. Только поведение домашних заданий/решений/оценок после удаления курса пока не определено.
10. Создающие `POST` курсов/занятий **не требуют обязательного `Idempotency-Key`**. Идемпотентность обязательна для отправки сообщения (`clientMessageId`), фонового удаления и внутреннего реестра `material_reference`.

### 0.2. Definition of Done — общий для каждого этапа

Этап завершён, только если одновременно:

- [ ] Поведение совпадает с соответствующими контрактами; маршрут/DTO/HTTP-код/права доступа не изменены произвольно.
- [ ] Реализованы сервисная логика, необходимые SQL-миграции, репозитории и интеграции — без «пустых» методов.
- [ ] Есть позитивные, негативные и (где возможны гонки) конкурентные тесты на **реальной PostgreSQL / S3 / Kafka среде через Testcontainers**.
- [ ] `./gradlew test` проходит; для интеграционных тестов есть воспроизводимая задача (`integrationTest` или единый `test`, согласно стилю репозитория).
- [ ] `./gradlew bootJar` проходит; Docker-образ продолжает собираться. Если добавлена новая миграция, она применяется к чистой БД.
- [ ] Нет секретов в Git, логах, DTO и ошибках. Ошибки API не раскрывают приватные сведения чужих курсов.
- [ ] README/`docs/` обновлены ровно в части сделанного. Нет описания будущего функционала как реализованного.
- [ ] В конце ответа Codex выдал: **(1)** изменённые файлы, **(2)** реализованное поведение, **(3)** выполненные команды и результаты, **(4)** непокрытые риски, **(5)** критерии DoD с отметками; затем остановился.

### 0.3. Рекомендуемая структура пакетов

Сохранять существующие соглашения репозитория; если проект новый, достаточно **package by feature** без избыточных абстракций:

```text
education-service/
  src/main/java/.../education/
    common/          # error, pagination, security context, clocks
    security/        # HTTP JWT, STOMP auth, permission checks
    integration/     # Identity client, object storage, Kafka
    course/          # course + course_student
    schedule/        # single lessons, series, exceptions, conflicts
    material/        # folders, files, ACL, references
    chat/            # history, attachment, STOMP send, moderation
    cleanup/         # cleanup_job, workers, leases
    outbox/          # outbox_event, publisher
  src/main/resources/db/migration/
  src/test/java/.../
  Dockerfile
  .dockerignore
```

**Принцип:** Controller/WS adapter → application service → repository/integration port. Прямые операции с MinIO/Kafka не выполнять в HTTP-контроллерах; внешние вызовы не держать под длительной SQL-транзакцией. Не создавать отдельные Gradle-модули для каждой папки без причины.

# ЭТАП 1. Инициализация проекта, MinIO, Dockerfile, воспроизводимый запуск

**Приоритет:** выполнить первым; этот этап специально более подробный.  
**Результат:** пустое, но рабочее приложение Education Service в локальной инфраструктуре; приватное объектное хранилище доступно из backend; есть тестируемая S3-абстракция, Dockerfile и базовые health-checks. **Бизнес-маршруты не реализовывать.**

## 1.1. Аудит существующего репозитория

**Что сделать:**

1. Найти текущий каталог сервисов и `docker/local`: имена контейнеров, Docker-сеть, env-файлы, PostgreSQL, Kafka, Redis; определить, запускается ли Education как часть общего Compose или в отдельном профиле.
2. Сверить настройки Gradle/JDK и пакеты в Identity. Проверить существующий `gradlew`, `.gitignore`, `.env.example`, `application*.yaml` и портовые коллизии.
3. Записать короткое описание принятого layout в README Education (не переписывать README всей платформы).
4. Зафиксировать команды локального запуска **с хоста** и **из Docker**: у адресов PostgreSQL/MinIO/Kafka будут разные hostname.

**Критерий:** Codex может назвать точные каталоги, запускаемые команды и зависимые контейнеры — без догадок о структуре репозитория.

**Проверки:** `java -version`, `./gradlew --version`, `docker compose -f <реальный-файл> config`; убедиться, что ранее рабочие контейнеры не сломаны.

## 1.2. Создать Spring Boot-приложение и настроить Gradle

**Что сделать:**

1. Создать сервис под фактическим именованием репозитория: Spring Boot **4.1.1**, Java toolchain **17**, Gradle Kotlin DSL, Gradle Wrapper (версию wrapper выбрать совместимую с Boot 4.1.1 и зафиксировать).
2. Подключить в нужном объёме: Spring Web MVC, Validation, Spring Security OAuth2 Resource Server, Spring Data JPA, PostgreSQL driver, Flyway + PostgreSQL support, Actuator, JUnit/Mockito/AssertJ, Testcontainers PostgreSQL/MinIO. Kafka/WebSocket можно подключить на профильном этапе, чтобы не создавать ложные обязательные зависимости на старте.
3. Для Boot 4 проверить актуальные артефакты стартёров (`spring-boot-starter-webmvc`, `spring-boot-starter-security-oauth2-resource-server` и т. д.) вместо механического копирования названий Boot 3.
4. Завести `application.yaml`, `application-local.yaml`, `application-test.yaml` и **только нужные** переменные окружения. Настроить `spring.jpa.hibernate.ddl-auto=validate` после появления миграций; схему создаёт Flyway, а не Hibernate.
5. Настроить единый UTC формат хранения абсолютного времени, UTC в API; для будущих правил расписания отдельно использовать `Europe/Moscow`.
6. Подключить логирование с request/trace ID при наличии общей инфраструктуры; не логировать JWT и секреты. Actuator: `/actuator/health/liveness`, `/actuator/health/readiness` (не считать доступ к S3 без теста гарантированным).
7. Добавить простой `@SpringBootTest` на поднятие контекста в `test`-профиле с изолированными зависимостями (для подключённого JPA использовать PostgreSQL Testcontainers либо корректно отключённую неиспользуемую автоконфигурацию), без продовых токенов/адресов.

**Критерии:** приложение стартует локально; Java 17; Gradle воспроизводим из wrapper; процесс корректно завершает работу; health отвечает без бизнес-эндпоинтов. Не допускается Hibernate `create`/`update` в качестве миграций.

**Тесты:** `contextLoads`, базовый `health` HTTP-тест, негативный тест отсутствия конфигурационных секретов (ошибка запуска должна быть понятной, без печати значений).

## 1.3. Подключить S3/MinIO как инфраструктуру

**Важная оговорка об образе (актуально на ноябрь 2026):** `minio/minio` и `minio/mc` из Docker Hub больше не являются надёжным источником образов. Для **локальной учебной разработки** использовать и проверить доступный закреплённый образ с `quay.io/minio/minio` (например, `RELEASE.2025-09-07T16-13-09Z`); это **архивная, не обновляемая сборка**, не рекомендовать её как безусловный production-вариант. Альтернатива для локального S3-совместимого окружения — поддерживаемый форк `pgsty/silo`; **не подменять MinIO форком молча**. Записать выбранный вариант в README и проверить реальный `docker pull`.

**Что сделать:**

1. Добавить в существующий Compose сервис объектного хранилища `minio`, persistent volume, внутренний порт S3 `9000`, консоль `9001`. Хостовые порты выбираются без конфликта с существующими.
2. `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` брать **из локального `.env`**, не коммитить. Для dev допустим bootstrap root, но клиент приложения по возможности должен использовать отдельные S3 credentials с минимальными правами; никогда не переносить root-пароль в production config.
3. Создать **приватный** bucket, например `education-private` (техническое решение этого плана; имя настраиваемое). Подготовить идемпотентную и повторяемую инициализацию bucket: one-shot init сервис/скрипт S3 CLI либо dev bootstrap. **Не создавать публичную anonymous policy.**
4. Разделить в bucket префиксы: `materials/`, `chat/`, `tmp/`; объектные ключи генерирует сервер, они уникальны/непереиспользуемы и не совпадают с именем файла от пользователя.
5. Сохранить S3 данные в volume; повторный `up/down` без `-v` не должен удалять объекты. `down -v` в инструкции обязательно пометить как уничтожение локальных данных.
6. В README явно показать различие endpoint:
   - приложение запущено на host: `http://localhost:9000` (или фактический проброшенный порт);
   - приложение в одной Docker-сети: `http://minio:9000`.
7. Добавить профиль/переменные `EDUCATION_S3_ENDPOINT`, `EDUCATION_S3_BUCKET`, `EDUCATION_S3_ACCESS_KEY`, `EDUCATION_S3_SECRET_KEY`. Не вводить S3-hostname `localhost` внутрь контейнера Education.

**Ориентир Compose:** интегрировать *фрагмент* в существующий файл, а не создавать второй несовместимый стек. Версию образа сначала проверить командой `docker pull`.

```yaml
services:
  minio:
    image: quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z
    command: server /data --console-address ':9001'
    environment:
      MINIO_ROOT_USER: ${MINIO_ROOT_USER:?set in local env}
      MINIO_ROOT_PASSWORD: ${MINIO_ROOT_PASSWORD:?set in local env}
    ports:
      - '9000:9000'
      - '9001:9001'
    volumes:
      - education-minio-data:/data
    # readiness/init реализовать отдельно: не предполагать наличие curl/wget в image

volumes:
  education-minio-data:
```

**Проверки (реальная среда):**

- Чистый Compose создаёт bucket и затем перезапускается без ошибки «bucket already exists».
- Объект можно `PUT`, `GET`, `STAT`, `DELETE` с сервисными credentials; `GET` несуществующего объекта даёт диагностируемую ошибку.
- Неаутентифицированный HTTP-запрос к приватному объекту не возвращает его содержимое.
- Из контейнера Education DNS-имя `minio` достижимо; S3 endpoints не указывают на консоль `9001`.
- Создать объект, перезапустить сервис MinIO без удаления volume, прочитать тот же объект.

## 1.4. Реализовать единую S3-абстракцию внутри backend

**Что сделать:**

1. Подключить Java SDK `io.minio:minio` актуальной *проверенной совместимой* версии; версию зафиксировать в Gradle/каталоге версий. Не разносить вызовы SDK по контроллерам.
2. Создать конфигурацию с валидацией endpoint/bucket/credentials через `@ConfigurationProperties`; один `MinioClient` bean.
3. Создать узкий интерфейс, например:

```java
public interface ObjectStorage {
    void put(String objectKey, InputStream body, long size, String contentType);
    InputStream get(String objectKey);
    void delete(String objectKey); // повторное удаление отсутствующего объекта — успех
    boolean exists(String objectKey);
}
```

   При реализации не загружать весь файл в `byte[]`; корректно **закрывать поток** после чтения/записи, делать буферизацию потока; зафиксировать смысл `size=-1`/multipart SDK, не использовать бесконечный `readAllBytes()` для больших файлов.
4. Выделить генератор ключей (`materials/<uuid>`, `chat/<course-id>/<uuid>`, `tmp/<uuid>`) и фабрику безопасных метаданных. Полный `objectKey` **не включать** в публичные DTO, exception messages или access logs.
5. Реализовать контролируемое отображение S3-ошибок: недоступность хранилища → ошибка зависимости/неуспех операции; повторная очистка несуществующего объекта → идемпотентный успех.
6. **Не открывать временный тестовый endpoint `POST /upload`**. Smoke test выполнить тестовым кодом и CLI.

**Критерий:** все будущие материалы и чат используют одну S3-интеграцию, но имеют **разные таблицы/жизненные циклы**. Нет общедоступного bucket, нет прямых URL MinIO в JSON.

**Тесты:** unit-тесты на генератор ключей/валидацию конфигурации; integration test с настоящим S3-контейнером: потоковая запись/чтение бинарных данных, контроль размера и Content-Type, повторный DELETE, чтение отсутствующего объекта, уникальность ключей, недоступность сервера.

## 1.5. Dockerfile, .dockerignore и контейнерный запуск

**Что сделать:**

1. Создать multi-stage Dockerfile: stage сборки на JDK 17 через `./gradlew bootJar`, runtime на JRE 17. Копировать Gradle wrapper/скрипты отдельно для build cache; не полагаться на глобально установленный Gradle.
2. В Gradle настроить воспроизводимое имя `bootJar`, например `education-service.jar`, чтобы `COPY --from=build` не зависел от glob для `plain.jar`.
3. В runtime запускать **non-root**, не включать dev secrets в image/ARG, использовать `ENTRYPOINT` в exec-форме, передавать JVM-настройки и конфигурацию через env/`JAVA_TOOL_OPTIONS`.
4. Создать `.dockerignore` минимум для `.git`, `.gradle`, `build`, IDE-файлов, `.env`, ключей JWT, `dev_secrets`. Не копировать весь монорепозиторий без нужды.
5. Подключить service к существующей Docker-сети, правильным переменным БД/S3/Kafka; конфигурация `SPRING_PROFILES_ACTIVE=local` только для локального Compose.
6. Настроить порядок запуска/health там, где это действительно возможно. **Не путать** `depends_on` с гарантированной готовностью зависимостей; сделать понятный retry/fail-fast и status readiness.
7. Добавить раздел «как собрать и запустить» в README с явными проверками.

**Ориентир Dockerfile** (адаптировать `COPY` к действительному build context репозитория):

```dockerfile
FROM eclipse-temurin:17-jdk AS build
WORKDIR /workspace
COPY gradlew settings.gradle.kts build.gradle.kts ./
COPY gradle/ gradle/
RUN chmod +x gradlew && ./gradlew --no-daemon help
COPY src/ src/
RUN ./gradlew --no-daemon bootJar

FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=build /workspace/build/libs/education-service.jar /app/app.jar
USER 10001:10001
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

**Критерии:** image собирается из чистого checkout, запускается без ручной установки JDK/Gradle, backend из контейнера видит MinIO/PostgreSQL; image не содержит секреты; процесс работает не от root; health endpoint работает.

**Тесты:**

```bash
./gradlew clean test bootJar
docker compose -f docker/local/<фактический-compose>.yaml config
docker compose -f docker/local/<фактический-compose>.yaml up -d --build
# далее: health/readiness, логи, проверки доступа S3
```

Негативный сценарий: неправильный пароль S3/остановленный MinIO приводят к ясной ошибке/`readiness=DOWN` для S3-зависимого сервиса (с выбранной политикой), но не к выдаче пароля в логи. Проверить повторный `up` и сохранение данных.

# ЭТАП 2. Общая инфраструктура HTTP, JWT, Identity и PostgreSQL

**Что делаем:** фундамент авторизации, межсервисных запросов, ошибок и миграций, прежде чем писать курсы.

**Как:**
1. Сверить JWT Identity: JWKS/публичный RSA-ключ, `issuer=rp-identity` (если соответствует текущей конфигурации), валидация подписи/времени/issuer/ролей. Не доверять неподписанным claims. HTTP SecurityFilterChain: публичны только предусмотренные health endpoints, бизнес API защищён.
2. Вынести `CurrentUser`, `PermissionService`; различать `TEACHER`, `STUDENT`, `ADMIN`, несколько ролей у одного пользователя; роль в JWT **сама по себе не доказывает**, что преподаватель владелец конкретного курса.
3. Подключить Identity HTTP client для получения/проверки пользователя, текущего ФИО, `blocked`, роли STUDENT. Настроить явные timeouts, правильное сообщение при `503`, не считать любой сбой Identity равным «ученик не найден». Не придумывать пути Identity — сверить текущие реальные endpoints. Уточнить механизм актуализации блокировки пользователя.
4. Создать `ProblemDetail`/`application/problem+json` + `code`, корректные 400/401/403/404/409/413/415/422/503, глобальные обработчики ошибок и валидацию DTO.
5. Создать инфраструктуру keyset-cursor: opaque cursor, проверка формата, лимиты, привязка к запросу/курсу там, где требуется. Для списков `limit=30` default, max 100; для чата позднее отдельный `before`, default 50.
6. PostgreSQL URL/user/pass — отдельные env Education, не переиспользовать пароль общей БД без настройки. Миграции Flyway (начиная с таблиц следующего этапа), `ddl-auto=validate`, UTC/timestamptz. Реальную БД в integration test поднимать с Testcontainers.
7. Добавить тестовый способ выдавать **подписанные тестовые JWT** или mock проверку ресурс-сервера без ослабления production SecurityFilterChain.

**Тесты:** просроченный/чужой issuer/неверная подпись; несколько ролей; `blocked=true` → доступ запрещён согласно правилам платформы; Identity таймаут → 503; тест 400 на плохой UUID/limit/cursor; контекст `local`/`test` стартует независимо; миграции Flyway повторно применяются без повреждений.

# ЭТАП 5. Разовые занятия и месячный календарь

**Что:** `single_lesson`, `POST/PATCH .../lessons`, `POST .../cancel`, `GET /courses/{id}/schedule?month=YYYY-MM`, `GET /me/schedule?month=...`.

**Как:**
1. Flyway таблица `single_lesson`, FK на `course`, `timestamptz`, CHECK на 5–300 минут и `ends_at>starts_at`, индекс `(course_id,starts_at)`.

3. Отмена разового урока **физически** удаляет запись. Outbox-событие отмены и переноса добавить в этапе 7 в **той же транзакции**, не считать функциональность финальной до этапа 7.
4. Возвращать календарь **одного московского месяца**, sorting by actual `startsAt`; `me/schedule` объединяет собственные и зачисленные курсы текущего пользователя, не раскрывает чужие.

# ЭТАП 6. Бессрочные серии, исключения, остановка

**Что:** `lesson_series`, `lesson_exception`, виртуальные вхождения и REST-маршруты серий/переносов/отмен.

**Как:**
1. Flyway: `lesson_series` с `start_date` по Москве, уникальными `weekdays` 1..7, `start_time`, `duration_minutes`, `stop_from_date` nullable; `lesson_exception` с UNIQUE `(series_id,original_date)`, `kind CANCELLED|RESCHEDULED`, `new_starts_at/new_ends_at`, `reason`.
2. Вычислять вхождения **на лету**, для запрошенного месяца. Не генерировать бесконечные строки в БД. Идентичность конкретного вхождения — `(seriesId, originalDate)`, а не новая дата переноса.
3. Перенос одного вхождения: upsert исключения `RESCHEDULED` под тем же ключом, новое фактическое время может попасть в другой месяц. Для месяца B необходимо запросить также исключения с `newStartsAt` в B даже когда `originalDate` в A.
4. Отмена одного вхождения: `CANCELLED`, **не показывать** в календаре и не восстанавливать через API. Попытка переноса отменённого — `409 LESSON_CANCELLED`.
5. Остановка серии: исходные даты `originalDate >= stopFromDate` не возникают. **Перенос с `originalDate < stopFromDate` остаётся**, даже если новый `startsAt` позже даты остановки.
6. Правила на несколько дней с одним временем в одной серии; при разных временах — разные серии.

**DoD:** календарь корректен для всех ветвей виртуальных вхождений, включая переходы между месяцами; серия действительно бессрочная, кроме `stopFromDate`.

**Тесты:** разные дни/месяцы/год; повторение нескольких weekdays; invalid weekdays (0,8,пусто,дубли); повторный перенос → одно исключение; перенос между месяцами без дублей; отмена и повторный cancel; нельзя переносить отменённое; дата остановки inclusive; **регрессия 15→25 декабря и stopFromDate=20 декабря — 25-е показано**; исходное 25-е не появляется; из JVM с UTC и другой TZ результат одинаков.

# ЭТАП 7. Пересечения расписания + transactional outbox → Kafka

**Что:** предупреждение о пересечениях при создании/переносе/зачислении; Kafka-события переноса/отмены/остановки серии.

**Как:**
1. Написать единый `ScheduleConflictService`, проверяющий пересечение `[start,end)` c занятиями **преподавателя и зачисленных учеников** во всех их активных курсах, включая виртуальные регулярные занятия и переносы. Не передавать клиенту приватные названия/ID чужих курсов.
2. `confirmConflicts=false` + есть пересечения → `409 SCHEDULE_CONFLICTS`, список `{subjectType,subjectId,startsAt,endsAt}`, **без изменения БД**. `confirmConflicts=true` → повторная проверка перед сохранением и сохранение даже при конфликте. При создании серии проверять только следующие 30 дней.
3. Подключить вызовы conflict-checker к этапам 4–6: при зачислении, разовом занятии, серии и переносах. Сценарии, ранее помеченные как неполные, становятся завершёнными.
4. Flyway `outbox_event`: ID события, aggregate, type, payload jsonb, created_at, published_at; индекс неопубликованных. В **одной PostgreSQL-транзакции** записывать изменение расписания и событие `LessonRescheduled`, `LessonCancelled`, `LessonSeriesStopped`.
5. Отдельный publisher читает непубликованные события, отправляет в Kafka, только после подтверждения помечает published. Доставка **at least once**, `eventId` всегда стабилен при retry; потребитель должен дедуплицировать.
6. **Схема Kafka payload в REST-документе предварительная**. До внешней интеграции закрепить внутреннюю v1-схему в отдельном контракте/ADR, не называть её ранее утверждённой. Не придумывать работоспособный notification consumer.

**DoD:** 409 без коммита, подтверждение позволяет сохранить, outbox переживает сбой Kafka и рестарт без потери, не публикует события из откатившихся транзакций.

**Тесты:** учитель со своими двумя курсами; ученик в двух курсах; пересечение на границе (конец A = начало B не конфликт); новая серия проверяет 30 дней; без confirmation нет ни урока, ни outbox; при confirm сохранение; rollback → нет outbox; Kafka недоступна → непубликованная строка; Kafka восстановилась → событие; два publisher → нет конкурентной порчи строк; возможный повтор delivery → тот же eventId; отмена/остановка производят события.

# ЭТАП 8. Долговечный механизм асинхронной очистки (сначала инфраструктура)

**Что:** `cleanup_job`, воркер, leases, retry/backoff, безопасная последовательность MinIO → PostgreSQL. Не реализовывать пока публичные DELETE файлов/курсов до конкретных обработчиков.

**Как:**
1. Flyway `cleanup_job` с полями проекта: `id, resource_type, resource_id, status, attempts, next_attempt_at, locked_until, lease_token, last_error, created_at, updated_at`. Типы `COURSE`, `CHAT_MESSAGE`, `MATERIAL_FILE`, `MATERIAL_FOLDER`; статусы `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`. Partial unique index на незавершённые задачи одного ресурса.
2. Создать dispatcher/handlers по `resource_type`, не разветвлять огромный метод на десятки switch. Handler идемпотентен.
3. Захват пачки через короткую транзакцию `FOR UPDATE SKIP LOCKED`; назначить lease+token, затем **освободить SQL-транзакцию до операций MinIO**.
4. После успеха сделать финальную короткую SQL-транзакцию с проверкой lease token. При ошибке сохранить `attempts/last_error/next_attempt_at`, exponential backoff с ограничением и джиттером, статус `FAILED`/сигнал мониторинга по исчерпании политики; не терять задачу.
5. При истечении lease и рестарте обработчик может продолжить. Не позволять старому worker завершить чужую новую аренду. Долго выполняемое удаление не должно финализироваться после смены владения.
6. Метрики/логи: число pending/processing/failed, возраст задач, ретраи, длительность очистки, идентификаторы ресурсов без секретов. Не открывать публичный GET статуса.

**DoD:** механизм надёжен без специфики конкретных таблиц; при двойном запуске worker не повреждает данные. Удаление отсутствующего S3 объекта = успех.

**Тесты:** два worker на одну БД захватывают без дублей; авария после S3 delete, но до SQL → безопасный retry; MinIO недоступен → retry; смена lease → старый worker не финализирует; рестарт → recovery; повторная постановка одной незавершённой задачи → тот же job; `FAILED` виден в логе/метриках; нельзя потерять объектные ключи до S3-подтверждения.

# ЭТАП 10. ACL материалов: папки, наследование, file override, доступ через курс

**Что:** `folder_course_access`, `file_course_access`, управление разрешениями и чтение файлов учеником через его курс.

**Как:**
1. Flyway: `folder_course_access(folder_id,course_id)` и `file_course_access(file_id,course_id,allow_read)`, FK к Education tables; соответствующие индексы.
2. `PUT/DELETE .../folders/{id}/course-access/{courseId}` — владелец материалов/Admin, только на допустимый курс; повторный PUT идемпотентен.
3. `PUT/DELETE .../files/{id}/course-access/{courseId}` — **явное** allow/deny override. Отсутствие строки означает наследование от ближайшего/любого предка с грантом (в модели нет отрицательных правил папок).
4. Расчёт для конкретного ученика: актуальное членство хотя бы в одном активном курсе; для проверяемого курса явная запись файла имеет приоритет над папками-предками; при отсутствии override ищем грант папки по цепочке предков. Запрет в одном курсе не отменяет разрешение в другом курсе.
5. `GET /courses/{courseId}/materials` — плоский курсорный список доступных файлов; `GET /courses/{courseId}/materials/files/{fileId}/content` — повторно проверить ACL/членство и скачать через backend, не раскрывая object_key.
6. После перемещения файла наследование меняется сразу; explicit override сохраняется. При удалении членства доступ через этот курс прекращается.

**DoD:** правила работают при глубокой вложенности и нескольких курсах, без глобального «разрешено навсегда» по UUID файла.

**Тесты:** грант на родителя → дочерние файлы и вновь созданные; явный allow в закрытой папке; явный deny в открытой; отсутствие override; перемещение между открытой и закрытой папками; доступ из другого курса перекрывает deny первого; исключение ученика/удаляемый курс → отказ; чужой teacher не управляет ACL; 401/403/404 и попытки скачать по чужому `courseId`.

# ЭТАП 11. Реестр ссылок Assignment и безопасное удаление библиотеки

**Что:** `material_reference`, служебные регистрация/освобождение ссылки, `DELETE` файла и папки через cleanup worker.

**Как:**
1. Flyway `material_reference`: стабильный `referenceId`, `file_id`, `consumer_service=ASSIGNMENT`, `consumer_entity_id`, уникальность связи `(file,consumer_service,entity)`; индексы.
2. Закрыть `/internal/v1/materials/.../references` **сервис-сервис авторизацией**; обычный пользовательский JWT нельзя принимать как доверенный internal token. Конкретный механизм зависит от принятой инфраструктуры Identity; если не настроен — не оставлять endpoint публичным. Код доменной регистрации/снятия ссылки и его тесты реализовать независимо.
3. При регистрации блокировать **строку `material_file`**, проверять ACTIVE, обеспечивать идемпотентность по `referenceId` и content, `409 REFERENCE_ID_CONFLICT` для повторного ID с иным payload, `409 MATERIAL_DELETING` при удалении.
4. `DELETE /materials/files/{id}`: под той же блокировкой проверить отсутствие ссылок; если есть — `409 MATERIAL_IN_USE` **без смены состояния**. Иначе `ACTIVE → DELETING` и `cleanup_job(MATERIAL_FILE)` **в одной транзакции**, ответ `202`. Worker сначала удаляет S3 объект, затем физически строку и ACL.
5. `DELETE /materials/folders/{id}`: рекурсивно проверить **все дочерние файлы** и refs. Если хотя бы один используется, отказать без частичного удаления. Защитить удаляемое дерево от новых файлов/перемещений/registrations (единый порядок блокировок/locking protocol); перевести subtree в `DELETING` с одной задачей `MATERIAL_FOLDER`. Воркер удаляет все S3-объекты до финального удаления SQL-дерева.
6. Повторный DELETE уже удаляемого ресурса возвращает существующий `cleanupJobId`; если физически удалён — `404`; не удалять `cleanup_job` каскадом.

**DoD:** файл с хотя бы одной ссылкой Assignment удалить нельзя **даже админу**; нельзя обойти запрет удалением его папки; конкурирующие операции не позволяют успеть зарегистрировать ссылку после начала удаления.

**Тесты:** 1/2 ссылки, повторная регистрация, reuse ID с иным payload, release после удаления привязки; два конкурентных register; register vs DELETE файла → ровно один допустимый исход; DELETE папки с используемым потомком → 409 и никакого DELETING; upload/move vs DELETE папки → нет потерянных S3 объектов; с S3 ошибкой статус DELETING и worker retry; повтор DELETE idempotent; после полного удаления S3 404, metadata отсутствует; чужие материалы не удаляются.

# ЭТАП 12. REST-чат: режим, хранение сообщений, история и курсоры

**Что:** модели `chat_message`, `chat_send_receipt` и REST чтение истории; менять режим NORMAL/ANNOUNCEMENTS. **Отправку сообщений по HTTP не создавать**.

**Как:**
1. Flyway `chat_message`: `course_id`, `author_id`, `author_role`, **`author_display_name` snapshot**, `body <= 4000`, `client_message_id`, `state`, `created_at`; индексы `UNIQUE(course,author,client_message_id)` и `(course,created_at DESC,id DESC) WHERE state='ACTIVE'`.
2. Flyway `chat_send_receipt`: PK `(course_id,author_id,client_message_id)`, `message_id` **без FK** на `chat_message`, `request_hash`, created_at; хранить до физического удаления курса **без TTL**. Не хранить в receipt текст/имя файла. Канонический payload/hash продумать без утечки короткого текста через обычный неизменяемый хеш (keyed hash предпочтительнее).
3. `GET/PATCH /courses/{id}/chat/settings`: owner/admin меняет, текущие ученики могут читать. `ANNOUNCEMENTS`: ученик только читает; преподаватель/admin отправляют даже в этом режиме.
4. `GET /courses/{id}/chat/messages?limit=50&before=...`: текущий ученик, владелец/admin; ключ `(created_at DESC,id DESC)`, `limit 1..100`; `before` — непрозрачный курсор, привязан к конкретному курсу, декодируемый **без повторного наличия опорного сообщения**.
5. В DTO `author.displayName` брать исключительно из snapshot; только ACTIVE сообщения, без заглушек; `attachments: []` до этапа 13, позже реальные метаданные/URL backend.
6. Правило жизни: ученик читает всю историю, включая до зачисления; исключённый — ничего. Флаг `canSendMessages=false` **не** влияет на чтение.

**DoD:** выдача истории корректна и безопасна; нет REST отправки сообщения; snapshot ФИО остаётся прежним при изменении Identity.

**Тесты:** 0/1/101 сообщений, лимиты 1,50,100,101; одинаковое createdAt с id tie-breaker; cursor опорное сообщение физически удалено; курсор другого курса → 400; tampered cursor → 400; student after enrollment видит старые сообщения; revoked → 403/404; `canSendMessages=false` всё ещё читает; `DELETING` нет; изменение имени Identity не меняет authorDisplayName; `ANNOUNCEMENTS` режим хранится в course.

# ЭТАП 13. Вложения чата: временная загрузка, READY, скачивание, TTL

**Что:** `chat_attachment`, REST upload и download, жизненный цикл `UPLOADING → READY → ATTACHED` (ATTACHED позже в этапе 14), удаление неиспользованных файлов через 24 часа.

**Как:**
1. Flyway `chat_attachment`: `id, course_id, message_id NULL, uploader_id, object_key UNIQUE, original_name, mime_type, size_bytes, upload_state, created_at, expires_at` + FK/индексы. Временная запись **создаётся до S3 upload**.
2. `POST /courses/{id}/chat/attachments`: только текущий вправе отправлять; owner/admin всегда, student только `NORMAL` и `canSendMessages=true`. Через backend multipart, проверять размер **20 000 000 байт**, whitelist `JPG/JPEG/PNG/WEBP/PDF/DOCX/XLSX/TXT`; расширение, объявленный MIME и действительное содержимое, насколько возможно; блокировать исполняемые/неподдерживаемые payload.
3. Держать файлы приватно в MinIO, потоково. После загрузки в транзакции проверить `course=ACTIVE`, право отправки и то, что upload ещё не истёк/не забран уборщиком, затем `READY`. Если проверка не проходит, не публиковать файл; поставить на уборку S3.
4. TTL = 24 часа **от создания временной записи** (не от READY), уборка не касается `ATTACHED`. Защититься от гонки: cleanup не должен удалить S3 объект, который ещё пишет активный uploader, и поздняя загрузка не может создать «забытый» объект. Использовать lease/синхронизацию и reconciliation временного префикса.
5. `GET /courses/{id}/chat/messages/{messageId}/attachments/{attachmentId}/content`: только после ATTACHED, ACTIVE course+message, соответствует course/message, valid membership. Потоковая отдача через backend, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, безопасный Content-Disposition.
6. **Не вводить** в MVP отдельный публичный DELETE временного вложения и не делать URL MinIO публичным.

**DoD:** временное вложение принадлежит только uploader и **не скачивается через публичный backend download API до привязки**; после TTL исчезает из БД/MinIO; прикреплённые остаются до удаления сообщения.

**Тесты:** все 8 расширений и MIME; запрет .exe/переименованного exe; размер 20 000 000 принят, 20 000 001 отвергнут (`413`), ошибка формата `415`; пустой/запрещённый MIME; multipart обрыв, MinIO timeout, course became DELETING, uploader excluded during upload; TIME=23:59 vs 24:00; параллельный TTL cleaner и незавершённый PUT; ATTACHED не удаляется по TTL; прямой GET по S3 без credentials не проходит; к чужому messageId/attachmentId доступ закрыт; скачивание в no-store.

# ЭТАП 14. WebSocket/STOMP: отправка, post-commit ACK, дедупликация

**Что:** единственный маршрут создания сообщений в реальном времени и подписки на чат.

**Как:**
1. `GET /ws`; STOMP `CONNECT` с `Authorization: Bearer <JWT>`, валидировать JWT; автор из Principal. Клиент `SEND /app/courses/{courseId}/chat.send`, `SUBSCRIBE /topic/courses/{courseId}/chat`, личный ответ `/user/queue/chat.responses`.
2. На `CONNECT` — аутентификация, на каждом `SUBSCRIBE` — актуальное право чтения конкретного курса, на **каждом SEND** — право отправки + ACTIVE course, роль, `ANNOUNCEMENTS`, персональный запрет. Не позволять wildcard-подписку обойти ACL.
3. Требование договора: после исключения из курса/блокировки пользователя прекращается доступ **включая уже существующую WS-сессию**. Для локального исключения закрывать/отписывать активную сессию. Для внешней блокировки из Identity потребуется механизм оперативного отзыва (событие/инвалидация/проверка); не заявлять мгновенную гарантию без него. Зафиксировать фактическую границу реализации, пока межсервисный контракт не доступен.
4. DTO отправки: `clientMessageId` UUID обязателен; `text` null или до 4000; максимум **5** уникальных attachmentIds, по 20M каждый, сумма до **50 000 000**; пустые пробелы без файлов запрещены.
5. В транзакции: проверить права → найти ранее сохранённый receipt по `(course,author,clientMessageId)` **до проверки READY вложений**; при одинаковом canonical payload и существующем ACTIVE message вернуть старый ACK, при ином — `CLIENT_MESSAGE_ID_CONFLICT`, при физически удалённом — `MESSAGE_ALREADY_DELETED`.
6. При новой отправке атомарно блокировать выбранные READY attachments, проверить course/uploader/size/count, создать `chat_message` с snapshot displayName и `chat_send_receipt` (одна транзакция), перевести attachments в `ATTACHED`/задать `message_id`.
7. **Только ПОСЛЕ COMMIT** отправить автору `MESSAGE_ACCEPTED`, участникам `MESSAGE_CREATED`; содержимое `message` идентично REST DTO, включая backend `downloadUrl`.
8. Ошибки обычной команды — `MESSAGE_REJECTED` на личный destination, не разрывать WS; невалидный JWT на CONNECT — STOMP ERROR/закрытие.
9. Simple broker **одного инстанса** достаточно; не вводить broker relay/Kafka для realtime чата в MVP. Запрещено обещать гарантированную доставку событий или глобальный порядок.

**DoD:** нет двойной записи при повторах; нет ACK до коммита; нет повторного `MESSAGE_CREATED` при retry; после reconnect корректный пользователь может снова подписаться.

**Тесты:** реальный STOMP клиент: valid/invalid/expired JWT; subscribe чужого курса; student NORMAL allowed/ANNOUNCEMENTS denied, admin ANNOUNCEMENTS allowed; person canSend=false denied; author ID невозможно подменить payload; пустой текст, 4000/4001, 0/1/5/6 attachments, 50M/50M+1; READY чужого uploader, другой курс, ATTACHED/expired; два параллельных SEND одного clientMessageId → ровно одна БД-запись и один `MESSAGE_CREATED`; повтор identical → старый ACK; изменённый text/IDs → conflict; DELETE исходного message → MESSAGE_ALREADY_DELETED; искусственный SQL rollback → нет ACK и нет CREATED; post-commit ACK приходит после видимости строки другому SQL connection; STOMP ошибка не обрывает живое соединение; удаление из курса при активном WS → доступ прекращён.

# ЭТАП 15. Модерация чата, удаление сообщения и catch-up contract

**Что:** удаление сообщений согласно правам; `MESSAGE_DELETED`, безопасная S3-очистка; серверные гарантии восстановления истории.

**Как:**
1. `DELETE /courses/{id}/chat/messages/{messageId}`: учитель удаляет свои+учеников **своего** курса, admin — любые, ученик не удаляет вообще, учитель не удаляет сообщение администратора (если это не разрешено контрактом).
2. Только текст: в одной транзакции физически удалить message, не трогать receipt, `204`; после commit опубликовать `MESSAGE_DELETED`.
3. С attachments: в одной транзакции `ACTIVE→DELETING` и `cleanup_job(CHAT_MESSAGE)`; после commit `202` и `MESSAGE_DELETED`. С этого момента история/скачивание и новые retry уже не могут открыть содержимое. Worker удаляет S3 вложения, затем физически message+attachments; `chat_send_receipt` остаётся.
4. Событие `MESSAGE_DELETED` **после коммита скрытия**, не ждать удаления MinIO. `MESSAGE_CREATED`/`MESSAGE_DELETED` допускаются post-commit через outbox на той же инфраструктуре, но не создавать новый публичный журнал чата.
5. Серверная часть поддержки reconnect: REST-история остаётся source of truth; DTO не содержит DELETING. Frontend по контракту должен: подписаться → буферизовать WS события → **заменить** локальный список первой REST-страницей → применить буфер → догружать `before`. Не пытаться сделать гарантированное replay через event table.

**DoD:** после 202 file недоступен backend даже при известном UUID; физическое удаление при восстановлении S3; receipt защищает от воскрешения.

**Тесты:** роль student/teacher/admin, teacher vs admin message; text-only 204; attachment 202; сразу после commit download 404/403; MinIO упал между state change и delete → файл не скачивается, worker retry; повтор DELETE → одна задача; повтор SEND со старым clientMessageId после удаления → MESSAGE_ALREADY_DELETED; WebSocket event только post-commit; история не возвращает tombstone; курсор работает после удаления опорной строки; reconnect во время удаления не восстанавливает сообщение в списке.

# ЭТАП 16. Асинхронное удаление курса — обязательная функциональность MVP

**Что:** `DELETE /courses/{courseId}`, `DELETING + cleanup_job(COURSE)`, полная очистка принадлежащих курсу данных и **только** chat S3 objects.

**Как:**
1. Owner/admin инициирует DELETE: в короткой транзакции `SELECT course FOR UPDATE`, если ACTIVE → установить DELETING, создать cleanup-job, commit, вернуть `202 Accepted {resourceId,deletionState,cleanupJobId}`. Повтор в DELETING — **тот же** `cleanupJobId`; физически отсутствующий → 404.
2. С момента commit все REST/WS чтения и изменения курса запрещены, в т. ч. создание занятий, регистрацию членов, смену чата, SEND, загрузку/публикацию вложения, скачивание chat objects.
3. Защитить **гонки**: операции, начавшиеся до DELETE, не могут коммитить новую курсовую запись/ATTACHED после перехода DELETING; координировать активные upload и финализацию удаления. Поздно завершившийся S3 PUT не должен оставить «забытый» объект. Temporary objects удалять отдельно с надёжной сверкой.
4. Worker читает список chat object keys, удаляет их в MinIO, при ошибке делает retry. Нельзя терять ключи до подтверждения S3-удаления.
5. В **финальной SQL-транзакции** удалить chat attachments/messages/receipts, `lesson_exception`→`lesson_series`, `single_lesson`, `course_student`, `folder_course_access`, `file_course_access`, затем `course`; отметить job `COMPLETED`. Следить за FK и не удалять job каскадом.
6. Не удалять `material_folder`, `material_file`, S3-объекты **учебной библиотеки**, `material_reference`; права удалённого курса удаляются. Assignment Service пока в другой БД; **не симулировать** каскадное удаление заданий/решений/оценок.
7. Мониторинг ошибок/повторов внутренний, **публичный GET cleanup job не добавлять**.

**DoD:** курс исчезает из пользовательского API сразу после 202 и в итоге физически из БД; chat S3 bytes удалены; материалы учителя и реестр ссылок сохранены; восстановление после restart/retry работает.

**Тесты:** teacher/admin vs чужой teacher/student; удаление пустого курса; курс с расписанием, серией, исключениями, членствами, ACL, сообщениями и attachment в MinIO; немедленные REST/WS 404/409/отказ; повтор DELETE → один job; MinIO downtime → курс остаётся невидимым, job не теряется; S3 missing object → успех; worker restart → завершение; гонка DELETE + параллельные SEND/upload/enroll/move; SQL FK после удаления все целостны; **библиотечный файл с grant на удаляемый курс остаётся**, а grant удалён; `material_reference` остаётся; `cleanup_job COMPLETED` сохраняется; никакие данные Assignment не объявляются удалёнными.

| **5–7** | Расписание, серии, конфликты, Kafka outbox | Полный календарь/409 + Kafka retry |
| **8** | Cleanup-job dispatcher/worker | Retry, lease, два worker, restart |
| **9–11** | Библиотека, ACL, refs, удаления | Никаких file leaks/races, запрет удаления используемых |
| **12–15** | REST history, chat uploads, STOMP, moderation | Post-commit ACK, dedup, download ACL, deletion |
| **16** | Удаление курса | Полный каскад в Education, сохранение материалов |
| **17** | E2E, наблюдаемость, hardening | Полное выполнение контрактов |

**Особое правило для промежуточных этапов:** допустимо, что часть функционала ещё недоступна (например, enrollment conflict checks до этапа 7, реальное удаление файлов до этапа 11). Но тогда README и отчёт Codex явно помечают **«реализовано частично, зависит от этапа N»**, и нет фальшивых зелёных тестов.

## 18.2. Реестр межэтапных рисков

1. **Блокировки Identity и уже открытые WebSocket-сессии.** Спецификация требует оперативно прекращать доступ; конкретный event/revocation канал может не существовать. Codex должен реализовать проверяемую серверную защиту на SEND/SUBSCRIBE, немедленную локальную реакцию на исключение и отдельно зафиксировать зависимость блокировки от Identity, не обещать несуществующее мгновенное оповещение.
2. **Загрузка vs удаление.** Все chat/material files требуют staging, повторной проверки ACTIVE перед публикацией и защиты от поздних PUT. Только один 24h TTL не решает race. Это обязательные конкурентные тесты.
3. **Сервис-сервис авторизация Assignment.** Нельзя открыть `/internal/v1` наружу из-за отсутствия готового токена. Domain mechanics можно тестировать заранее, exposed API — только после безопасного механизма.
4. **Schema Kafka.** Исходный REST-документ даёт проектный payload, но не утверждённый окончательный контракт Notifications; версия/поля должны быть явно зафиксированы до интеграции потребителя.
5. **Расхождение физической схемы.** Согласованы 15 таблиц; `pending_upload` может быть отдельной *технической* таблицей для корректного lifecycle. Codex обязан объяснить необходимость и покрыть её тестами.
6. **Изображение MinIO.** Docker Hub minio/minio недоступен в 2026; архивная сборка Quay только для local demo. Изменение на Silo/AIStor требует явной фиксации и проверки совместимости, не является незаметным изменением хранилища.
7. **Никакой ACID между сервисами.** Education UUID из Identity/Assignment — внешние данные. SQL FK и SQL cascade через чужую БД не существует.
