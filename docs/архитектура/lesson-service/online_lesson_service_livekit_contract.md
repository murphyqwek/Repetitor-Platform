# Online Lesson Service — LiveKit integration

## 1. Infrastructure and PoC
Self-hosted LiveKit Server pinned supported image, Java/Kotlin server SDK, JS livekit-client. Verify versions and actual SDK signatures/config before coding. `LIVEKIT_URL` internal HTTP(S), `LIVEKIT_PUBLIC_URL` WSS reachable browser, key/secret env/secret store, webhook receiver configured. HTTPS/WSS, UDP media, TCP fallback and TURN as required by deployment; validate external IP/ICE behind NAT, mobile devices. `room.auto_create: false`, `room.enable_remote_unmute: false` (verify exact config for pinned version). No recording/egress. Max 10 room participants (8 students+owner+one admin), explicit room creation only. Do not expose API secrets or roomAdmin grants to browser.

## 2. Room state machine
`PROVISIONING → AVAILABLE` or `UNAVAILABLE` retry, `CLOSING → CLOSED`. Separate from STARTING/ACTIVE; provision independently of board but token only ACTIVE. Name `lesson-{lessonId}-{generation}`, unique durable generation, never reuse retired name even if empty room auto-closed. CreateRoom with stable name for same provisioning attempt, verify ListRooms/Get after unknown result, avoid duplicate generation on retry. Check room name/generation and state before marking AVAILABLE. LiveKit may auto-close empty room; reconciliation allocates new generation and provisions when required. No meeting restart or board reset. If old create completes after retirement/finish, durable orphan scan closes it; never issue token for retired name. On failure show fallback board/meetingUrl, retry backoff; recovered room emits status.

## 3. Tokens and moderation
POST video-token performs synchronous Identity/Education membership checks, local current state/permissions, admin slot, deadline and generation. Return url+token+generation+expiresAt (60 s initial TTL). Identity = user UUID string; roomJoin true, room specific, canSubscribe true, canPublish determined by per-source flags, allowed sources CAMERA/MICROPHONE/SCREEN_SHARE/SCREEN_SHARE_AUDIO (screen audio follows screen share), canPublishData=false because chat/board own STOMP, no roomAdmin/create/list/record grants. Server SDK signs; no storage/logs. New media connection same identity replaces old per verified LiveKit semantics; track SID and generation to fence old disconnect. Native reconnect handled by SDK; if reconnect fails/revoked/room generation differs, request fresh token, never retry retired room indefinitely.

Teacher/admin moderation through backend only: MutePublishedTrack(muted=true) on current camera/mic track(s), no remote unmute; one-shot mute does not prevent self-unmute. UpdateParticipant persistent source permission; persist application right before external change, rotate if old tokens allow forbidden publishing. Screen share audio included. Source grant removal and kick are not equivalent to immediate third-party revocation on self-hosted LiveKit. Use RemoveParticipant as best-effort in old room, not sufficient as security boundary.

## 4. Strict room rotation
On kick/course removal/Identity blocked/auth lease expiry or stale permission grants, lane SQL transaction revokes local access, increments generation (or reserves next generation) and creates durable ROTATE_MEDIA_ROOM with old/new names. Stop issuing old grants immediately. Close old room(s) first; confirm absent, then provision new room and mark AVAILABLE, notify allowed participants to reconnect. If old room cannot be confirmed closed, keep new media unavailable (fallback); do not claim physical removal. Old JWT (including refreshed) bound to retired room, auto-create disabled; no new tokens for revoked actor. Repeated rotations coalesce to latest desired generation, stale jobs never mark new status. All app subscriptions closed at local revoke. On finish close every generation, no further token. During unreachable media server cannot guarantee existing media stops instantly; external meeting link itself also not revocable. Test actual behavior including malicious rejoin using old refreshed tokens and old grants. Do not suggest short TTL alone sufficient.

## 5. Webhooks
`POST /internal/livekit/webhook` (separate ingress only for configured LiveKit, not user service JWT endpoint). Read raw body bounded, verify signed Authorization token + body hash via SDK receiver, reject invalid 401/400, no parsed-body reserialization for signature. Durable insert eventId unique before 2xx; if SQL unavailable 503, LiveKit retry best-effort. Process PENDING under lane, no guarantee all events delivered. Types room_started/room_finished/participant_joined/participant_left/participant_connection_aborted (check names with pinned SDK); unknown signed type safely ignore/record. Validate room name, lesson/generation, participant identity, participantSid, authoritative state; joined only after media established, leave specific SID not newest connection. On invalid join (not eligible) initiate remove/rotate; old events never revive finished lesson. Duplicate eventId no repeated state change. Use room/participant actual observation to resolve out-of-order events; timestamp is not a sufficient ordering guarantee.

## 6. Reconciliation and presence
Every15s ListRooms/ListParticipants for active/closing rooms with bounded timeouts, batch work; not on every pointer event. Confirmed active SID updates MEDIA; missing from successful response closes that observation; API failure → UNKNOWN rather than empty list. APP heartbeat separate; PRESENT if either confirmed, ABSENT only both known absent, else UNKNOWN. Stale observations not marked confirmed indefinitely. Teacher absence continuous 60m, UNKNOWN breaks confirmed absence streak; max6h always. No attendance from external Telemost. Recovery after restart requery live rooms, reconcile DB open connections; don't mark everyone absent solely from restart. Webhooks and reconciliation feed same presence reducer; late old generation ignored for current state. If app still usable during fallback teacher keeps board open. Media status unavailable not a lesson finish trigger.
