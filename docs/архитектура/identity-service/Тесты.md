# Identity Service — сценарии тестирования

**Статус:** черновик тест-плана  
**Основа:** согласованные требования Identity Service и перечень из раздела «Какие сценарии обязательно проверить».  
**Цель:** проверить бизнес-правила, корректность состояний и ограничение доступа. Тесты реализуются по мере разработки соответствующих функций.

## 1. Регистрация родителей

- [ ] **REG-P-01 — Успешная регистрация.** Родитель указывает свободный логин, корректный пароль и действующий код приглашения. Аккаунт создаётся, назначается роль `PARENT`, пароль не хранится открытым текстом, код больше нельзя использовать.
- [ ] **REG-P-02 — Занятый логин.** Регистрация с уже существующим логином отклоняется; новый аккаунт не создаётся.
- [ ] **REG-P-03 — Некорректный пароль.** Пароль, не соответствующий требованиям длины, отклоняется; аккаунт не создаётся.
- [ ] **REG-P-04 — Недействительный код.** Несуществующий, истёкший, отозванный или уже использованный код не позволяет зарегистрироваться.

## 2. Регистрация преподавателей

- [ ] **REG-T-01 — Успешная регистрация.** Пользователь регистрируется по действующей ссылке администратора; аккаунт создаётся с ролью `TEACHER`.
- [ ] **REG-T-02 — Просроченная ссылка.** Регистрация после истечения срока ссылки (1 день) отклоняется.
- [ ] **REG-T-03 — Повторное использование ссылки.** После успешной регистрации повторная попытка использовать ту же ссылку отклоняется.
- [ ] **REG-T-04 — Отозванная ссылка.** Отозванная администратором ссылка не позволяет зарегистрироваться.

## 3. Аутентификация и токены

- [ ] **AUTH-01 — Успешный вход.** По корректным логину и паролю пользователь проходит аутентификацию и получает предусмотренные cookies с токенами.
- [ ] **AUTH-02 — Неверный пароль.** Неверный пароль не позволяет войти; токены не выдаются.
- [ ] **AUTH-03 — Срок действия JWT.** Access-токен действителен в пределах срока 15 минут; просроченный токен не проходит проверку.
- [ ] **AUTH-04 — Обновление токенов.** С действующим refresh-токеном выдаются новые токены; старый refresh-токен нельзя использовать повторно после ротации.
- [ ] **AUTH-05 — Недействительный refresh.** Истёкший, отсутствующий или отозванный refresh-токен не позволяет обновить сессию.
- [ ] **AUTH-06 — Выход.** При logout refresh-токен отзывается, а auth-cookies очищаются. Повторное обновление по старому refresh-токену невозможно.

> **Требует отдельного решения:** должен ли ранее выпущенный access JWT немедленно отзываться при logout либо оставаться действительным до `exp` (не более 15 минут). В тестах необходимо закрепить выбранное поведение.

## 4. Приглашения родителей

- [ ] **INV-01 — Генерация кода.** Преподаватель создаёт приглашение; формируется случайный код из 12 заглавных латинских букв и цифр.
- [ ] **INV-02 — Срок действия.** Код действует 5 дней с момента создания; после истечения срока использовать его нельзя.
- [ ] **INV-03 — Просмотр своих кодов.** Преподаватель получает только собственные действующие приглашения; работают фильтрация и предусмотренная пагинация.
- [ ] **INV-04 — Отзыв кода.** Преподаватель может отозвать свой действующий код; после отзыва код не подходит для регистрации.
- [ ] **INV-05 — Запрет отзыва чужого кода.** Преподаватель не может отозвать приглашение другого преподавателя.

## 5. Регистрация детей

- [ ] **STU-REG-01 — Создание заявки.** Авторизованный родитель отправляет ФИО и класс ребёнка; заявка сохраняется со статусом ожидания.
- [ ] **STU-REG-02 — Подтверждение заявки.** Уполномоченный преподаватель или администратор подтверждает заявку; создаётся аккаунт ребёнка, устанавливается связь с родителем, заявка получает итоговый статус.
- [ ] **STU-REG-03 — Отклонение заявки.** Уполномоченный пользователь отклоняет заявку; её статус меняется, аккаунт ребёнка не создаётся.
- [ ] **STU-REG-04 — Повторная обработка.** Повторное подтверждение или отклонение уже обработанной заявки не создаёт второй аккаунт и не нарушает итоговое состояние.

## 6. Учётные данные детей

- [ ] **STU-CRED-01 — Генерация логина и пароля.** При создании ребёнка система выдаёт уникальный логин формата `st-XXXXXXXX` и сгенерированный пароль.
- [ ] **STU-CRED-02 — Просмотр родителем.** Родитель с подтверждённой связью с ребёнком может повторно получить его логин и текущий пароль согласно принятому требованию.
- [ ] **STU-CRED-03 — Запрет доступа к чужому ребёнку.** Другой родитель не может получить учётные данные ребёнка, с которым не связан.
- [ ] **STU-CRED-04 — Запрет доступа преподавателя.** Преподаватель и администратор не получают пароль ребёнка через операции просмотра заявок и учётных данных.

> **Проверка безопасности:** если текущий пароль должен показываться повторно, его нельзя хранить открытым текстом: требуется защищённое обратимое хранение отдельно от хеша, используемого для аутентификации. При проверке сценариев убедиться, что пароль не попадает в обычные ответы, журналы и кеш HTTP.

## 7. Профили

- [ ] **PROF-01 — Получение своего профиля.** Авторизованный пользователь получает `/users/me` с собственными разрешёнными полями и ролями.
- [ ] **PROF-02 — Редактирование своего профиля.** Пользователь изменяет разрешённые поля ФИО (и класс, если применимо); изменения сохраняются и видны при повторном запросе.
- [ ] **PROF-03 — Недопустимые изменения.** Запрос на изменение недоступных полей не позволяет изменить роль, блокировку, идентификатор и чужой профиль.

## 8. Поиск пользователей

- [ ] **DIR-01 — Фильтрация.** Поиск с `type=STUDENT` возвращает только учеников; с `type=PARENT` — только родителей. Параметр `fio` ограничивает результат по ФИО или его части.
- [ ] **DIR-02 — Курсорная пагинация.** При неизменных данных последовательное получение страниц через `nextCursor` не пропускает и не дублирует пользователей.
- [ ] **DIR-03 — Лексикографический порядок.** Сортировка выполняется по `surname`, `firstName`, `patronymic`, `id`, включая пользователей с одинаковыми ФИО и отсутствующим отчеством.
- [ ] **DIR-04 — Состав ответа.** Поиск родителей возвращает только ID и ФИО; поиск учеников дополнительно возвращает ID и ФИО их родителей. Пароли и логины в результатах поиска отсутствуют.
- [ ] **DIR-05 — Ошибочный курсор.** Некорректный курсор или курсор, не соответствующий фильтрам текущего запроса, отклоняется.

## 9. Администрирование

- [ ] **ADM-01 — Блокировка пользователя.** Администратор блокирует аккаунт; состояние сохраняется и учитывается при авторизации согласно принятой политике блокировок.
- [ ] **ADM-02 — Разблокировка пользователя.** Администратор снимает блокировку; аккаунт вновь может пользоваться разрешёнными функциями.
- [ ] **ADM-03 — Разграничение прав.** Пользователь без административных прав не может блокировать и разблокировать аккаунты.

---

## Общие правила для тестов

- Проверять не только HTTP-ответ, но и фактические изменения в PostgreSQL/Redis там, где это важно.
- Для негативных сценариев проверять отсутствие нежелательных побочных эффектов.
- Не использовать рабочую базу данных для автотестов; применять изолированное тестовое окружение.
- Для проверки сроков действия управлять временем детерминированно (например, через внедрённый `Clock`), а не через ожидание в реальном времени.
- Для критичных операций регистрации и подтверждения дополнительно предусмотреть тесты конкурентных запросов и атомарности.

**Открытые решения:** семантика отзыва access JWT при logout; политика действия блокировки на уже выданные токены; окончательные форматы ошибок и HTTP-статусы в соответствии с API-контрактом.
