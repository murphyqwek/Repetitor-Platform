# Identity Service — API

**Базовый префикс:** `/api/v1`

Все пути ниже указаны относительно этого префикса. Доступ к защищённым операциям определяется по текущей сессии пользователя. Access- и refresh-токены передаются в cookies.

Для POST/PATCH нужен CSRF: сначала `GET /auth/csrf`, затем заголовок `X-XSRF-TOKEN` со значением cookie `XSRF-TOKEN`. Ответы с профилями, приглашениями и паролями имеют `Cache-Control: no-store`.

## 1. Аутентификация

### 1.1. Вход

**Метод:** `POST`  
**Endpoint:** `/auth/login`

Авторизация пользователя по логину и паролю.

**Тело запроса:**

```json
{
  "login": "login",
  "password": "password"
}
```

**Результат:** access- и refresh-токены устанавливаются в cookies.

**Коды ответа:**
- `200 OK` — успешный вход.
- `401 Unauthorized` — неверный логин или пароль, либо аккаунт недоступен.

### 1.2. Регистрация родителя

**Метод:** `POST`  
**Endpoint:** `/auth/register/parent`

Регистрация родителя с использованием действующего кода приглашения.

Логин содержит 5–25 символов, пароль — 8–25. `policyVersion` — обязательная непустая версия принятой политики, до 100 символов. Время согласия сохраняет сервер. Погашение приглашения и создание аккаунта выполняются одной транзакцией.

**Результат:** `201 Created`, access- и refresh-токены устанавливаются в cookies. После регистрации нужно заполнить имя и фамилию через `PATCH /users/me`. До заполнения ФИО операции платформы возвращают 403; собственный профиль доступен. Отчество необязательно.

**Тело запроса:**

```json
{
  "login": "parent123",
  "password": "example-password",
  "invitationCode": "EXAMPLE12345",
  "policyVersion": "v1"
}
```

**Ошибки:**
- `400 Bad Request` — логин занят; логин или пароль не соответствует ограничениям длины; код отсутствует, истёк или недействителен.

### 1.3. Проверка ссылки регистрации преподавателя

**Метод:** `GET`  
**Endpoint:** `/auth/register/teacher/{code}`

Проверяет возможность регистрации по ссылке преподавателя. Просмотр ссылки не продлевает срок её действия.

**Тело запроса:**

**Коды ответа:**
- `200 OK` — ссылка действительна.
- `400 Bad Request` — ссылка не существует или истекла.

### 1.4. Регистрация преподавателя

**Метод:** `POST`  
**Endpoint:** `/auth/register/teacher/{code}`

Создаёт аккаунт преподавателя по действующей ссылке. Код берётся из пути запроса, срок ссылки — один день.

Ограничения логина, пароля и `policyVersion` такие же, как при регистрации родителя. Погашение ссылки и создание аккаунта атомарны. Результат: `201 Created`, токены в cookies. После регистрации преподавателю также нужно заполнить ФИО в собственном профиле.

**Тело запроса:**

```json
{
  "login": "teacher123",
  "password": "example-password",
  "policyVersion": "v1"
}
```

**Ошибки:**
- `400 Bad Request` — логин занят; логин или пароль не соответствует ограничениям длины; ссылка недействительна или истекла.

### 1.5. Обновление токенов

**Метод:** `POST`  
**Endpoint:** `/auth/refresh`

Принимает refresh-токен из cookie, выдаёт новый access-токен и ротирует refresh-токен.

**Коды ответа:**
- `200 OK` — токены успешно обновлены.
- `401 Unauthorized` — refresh-токен истёк или недействителен.

### 1.6. Выход из аккаунта

**Метод:** `POST`  
**Endpoint:** `/auth/logout`

Принимает токены из cookies, отзывает refresh-токен и очищает cookies. Уже выданный JWT без дополнительного механизма отзыва остаётся криптографически действительным до истечения своего срока.

**Коды ответа:**
- `200 OK` — выход выполнен.

## 2. Пользователи

### 2.1. Получение собственного профиля

**Метод:** `GET`  
**Endpoint:** `/users/me`

Возвращает профиль авторизованного пользователя.

**Пример ответа для ученика:**

```json
{
  "id": "a550d9c4-5d78-4c4e-85bb-c77950e5c2d2",
  "login": "st-K7M9P2RX",
  "firstName": "Арсений",
  "surname": "Стариков",
  "patronymic": "Дмитриевич",
  "roles": ["STUDENT"],
  "blocked": false,
  "createdAt": "2026-11-13T14:30:00Z",
  "nameRequested": true,
  "grade": 10
}
```

Поле `grade` содержит класс ученика, для остальных пользователей — `null`. `nameRequested` показывает, заполнены ли имя и фамилия. Пароль и его хеш в профиль не включаются.

### 2.2. Изменение собственного профиля

**Метод:** `PATCH`  
**Endpoint:** `/users/me`

Изменение доступных полей профиля (кроме пароля).

**Пример тела запроса:**

```json
{
  "firstName": "Арсений",
  "surname": "Стариков",
  "patronymic": "Дмитриевич",
  "grade": 10
}
```

Поле `grade` применимо только к ученику, диапазон — от 0 (дошкольник) до 11. Имя, фамилия и отчество — до 255 символов; имя и фамилия не могут быть пустыми. Неуказанные/null поля сохраняют прежнее значение; пустое отчество очищает его. Логин, пароль, роли и блокировка через эту ручку не изменяются.

### 2.3. Получение профилей своих детей

**Метод:** `GET`
**Endpoint:** `/students/my`

Доступ: `PARENT`. Возвращает массив профилей детей, связанных с текущим родителем, в формате раздела 2.1. При отсутствии детей возвращается `[]`.

### 2.4. Получение профиля ребёнка

**Метод:** `GET`
**Endpoint:** `/students/{id}`

Доступ: `PARENT`, только при наличии связи с ребёнком. Ответ имеет формат раздела 2.1. Чужой профиль недоступен: 403.

## 3. Приглашения родителей

### 3.1. Получение действующих приглашений

**Метод:** `GET`  
**Endpoint:** `/invitations/parents`

Возвращает список действующих приглашений, созданных текущим преподавателем, с пагинацией.

Преподаватель получает только созданные им приглашения, администратор видит все действующие приглашения.

**Query-параметры:**

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `page` | integer | `0` | Номер страницы, начиная с нуля |
| `size` | integer | `10` | Размер страницы, максимум 100 |

**Сортировка:** `createdAt DESC, id DESC` — от новых к старым, с устойчивым порядком при одинаковом времени.

**Пример запроса:**

```http
GET /api/v1/invitations/parents?page=0&size=10
```

**Пример ответа:**

```json
{
  "content": [
    {
      "id": 15,
      "createdAt": "2026-11-13T14:30:00Z",
      "expiresAt": "2026-11-18T14:30:00Z"
    },
    {
      "id": 14,
      "createdAt": "2026-11-12T10:00:00Z",
      "expiresAt": "2026-11-17T10:00:00Z"
    }
  ],
  "page": 0,
  "size": 10,
  "totalElements": 12,
  "totalPages": 2,
  "first": true,
  "last": false
}
```

**Правила:**
- Доступ пользователям с ролью `TEACHER` или `ADMIN`.
- Преподавателю возвращаются только его приглашения; администратору — все действующие.
- Не включаются использованные, отозванные и истёкшие приглашения.
- При отсутствии приглашений: `content: []`, `totalElements: 0`.
- Максимальный размер страницы — 100 элементов.

**Коды ответа:**
- `200 OK` — данные возвращены.
- `400 Bad Request` — некорректные параметры пагинации.
- `401 Unauthorized` — пользователь не авторизован.
- `403 Forbidden` — нет роли преподавателя или администратора.

**Замечание по модели:** если хранится только `code_hash`, исходный код не может быть восстановлен из хеша. В описанном ответе возвращаются метаданные приглашений.

### 3.2. Создание приглашения

**Метод:** `POST`  
**Endpoint:** `/invitations/parents`

Создаёт новый код приглашения для регистрации родителя. Действует 5 дней.

**Заголовок:**

```http
Idempotency-Key: 7b7fbe89-8d16-4855-ae97-e964c64fc67f
```

Заголовок используется для защиты от случайного повторного создания приглашения при повторной отправке запроса.

Возвращает код приглашения в чистом виде, строкой. Доступ: `TEACHER` или `ADMIN`.

**Коды ответа:**
- `200 OK` — приглашение создано.
- `401 Unauthorized` — пользователь не авторизован.
- `403 Forbidden` — нет роли преподавателя или администратора.

Заголовок `Idempotency-Key` обязателен, длина 1–128 символов. Повтор с тем же ключом в пределах срока идемпотентности возвращает прежний код; срок задаётся `identity.invitations.idempotency-ttl`, по умолчанию 15 минут.

### 3.3. Отзыв приглашения

**Метод:** `POST`  
**Endpoint:** `/invitations/parents/{id}/revoke`

Преподаватель отзывает собственное приглашение. Отозвать чужое приглашение преподавателю нельзя; администратор может отозвать любое. Успешный ответ: `200 OK`.

**Коды ответа:**
- `400 Bad Request` — приглашение не существует (согласно исходному описанию).
- `403 Forbidden` — пользователь не преподаватель или приглашение ему не принадлежит.

---

### 3.4. Получение действующих приглашений преподавателей

**Метод:** `GET`
**Endpoint:** `/invitations/teacher`

Доступ: `ADMIN`. Параметры `page`, `size`, сортировка и формат страницы совпадают с разделом 3.1. Элемент содержит `{id,createdAt,expiresAt}`; код и его хеш не возвращаются.

### 3.5. Создание приглашения преподавателя

**Метод:** `POST`
**Endpoint:** `/invitations/teacher`

Доступ: `ADMIN`. Требуется `Idempotency-Key` (1–128 символов). Возвращает код ссылки строкой, `200 OK`; срок действия — один день. Правила идемпотентности совпадают с разделом 3.2.

### 3.6. Отзыв приглашения преподавателя

**Метод:** `POST`
**Endpoint:** `/invitations/teacher/{id}/revoke`

Доступ: `ADMIN`. Успех: 200; отсутствующее приглашение: 400.

## 4. Регистрация детей

### 4.1. Создание заявки

**Метод:** `POST`  
**Endpoint:** `/student-requests`

Авторизованный родитель отправляет заявку на регистрацию ребёнка. Идентификатор родителя берётся из JWT.

**Тело запроса:**

```json
{
  "firstName": "Иван",
  "surname": "Иванов",
  "patronymic": null,
  "grade": 5,
  "policyVersion": "v1"
}
```

Имя и фамилия обязательны, до 255 символов; отчество — до 255 символов. Класс обязателен, от 0 до 11. `policyVersion` — обязательная версия принятой родителем политики, до 100 символов; время согласия сохраняет сервер.

**Результат:** `201 Created`, заявка в формате раздела 4.2.

**Заголовок:**

```http
Idempotency-Key: 7b7fbe89-8d16-4855-ae97-e964c64fc67f
```

`patronymic` может быть `null`. `Idempotency-Key` обязателен, длина 1–128 символов. Повтор с тем же ключом и данными возвращает прежнюю заявку; другие данные с тем же ключом — 409.

**Коды ответа:**
- `400 Bad Request` — некорректные данные заявки.
- `401 Unauthorized` — пользователь не авторизован.
- `403 Forbidden` — пользователь заблокирован или у него нет права создать заявку.

### 4.2. Получение своих заявок

**Метод:** `GET`  
**Endpoint:** `/student-requests/my`

Возвращает заявки текущего родителя, включая их статусы. Обработанные заявки сохраняются для истории.

Параметры: `page=0`, `size=10` (1–100). Сортировка: `id DESC`. Обёртка страницы совпадает с разделом 3.1.

**Пример элемента `content`:**

```json
{
  "id": 1,
  "parentId": "b550d9c4-5d78-4c4e-85bb-c77950e5c2d2",
  "firstName": "Иван",
  "surname": "Иванов",
  "patronymic": null,
  "grade": 5,
  "status": "PENDING",
  "studentId": null
}
```

Статусы: `PENDING`, `APPROVED`, `REJECTED`. После подтверждения заполнен `studentId`. Логины и пароли в ответ заявки не включаются.

### 4.3. Получение ожидающих заявок

**Метод:** `GET`  
**Endpoint:** `/student-requests`

Возвращает только `PENDING` для преподавателя или администратора. Пагинация и формат ответа совпадают с разделом 4.2.

В текущей схеме нет связи преподаватель–родитель, поэтому очередь общая для преподавателей и администраторов.

### 4.4. Подтверждение заявки

**Метод:** `POST`  
**Endpoint:** `/student-requests/{id}/approve`

Создаёт аккаунт ребёнка, генерирует логин `st-XXXXXXXX` и пароль, связывает ребёнка с родителем, отмечает заявку обработанной. Заявка блокируется в БД; аккаунт, роль, профиль, связь с родителем и новый статус сохраняются одной транзакцией. В профиль переносятся класс и согласие родителя.

**Ответ:** `200 OK`, заявка в формате раздела 4.2 без учётных данных. Повторное решение: 409; заявка не найдена: 404. При двух одновременных подтверждениях аккаунт создаётся один раз.

### 4.5. Отклонение заявки

**Метод:** `POST`  
**Endpoint:** `/student-requests/{id}/reject`

Отклоняет заявку и сохраняет результат рассмотрения. Доступ: `TEACHER` или `ADMIN`. Ответ: 200, заявка со статусом `REJECTED`; повторное решение: 409; заявка не найдена: 404.

### 4.6. Просмотр учётных данных ребёнка

**Метод:** `GET`  
**Endpoint:** `/students/{id}/credentials`

Возвращает логин и текущий пароль ребёнка родителю, имеющему подтверждённую связь с этим ребёнком. По принятому требованию пароль доступен родителю повторно, а не только при создании аккаунта.

**Пример ответа:**

```json
{
  "studentId": "a550d9c4-5d78-4c4e-85bb-c77950e5c2d2",
  "login": "st-K7M9P2RX",
  "password": "example-password"
}
```

**Требования безопасности:** проверка связи родитель–ребёнок; отсутствие пароля в логах; `Cache-Control: no-store`; при хранении восстановимого пароля — шифрование с отдельным защищённым ключом, не открытый текст. Хеш пароля для аутентификации хранится отдельно.

Реализация использует AES-256-GCM. Для запуска нужен `STUDENT_CREDENTIALS_KEY`: Base64 от 32 случайных байт. Ключ хранится вне БД и должен сохраняться между перезапусками. Смена ключа требует перешифрования данных; потеря ключа лишает возможности восстановить пароли, но не влияет на вход по BCrypt-хешу.

## 5. Поиск пользователей

### 5.1. Поиск учеников и родителей

**Метод:** `GET`

**Endpoint:** `/directory/users`

Поиск учеников или родителей по ФИО с использованием курсорной пагинации.

**Query-параметры:**

|Параметр|Тип|По умолчанию|Описание|
|---|---|---|---|
|`type`|string|Обязательный|`STUDENT` или `PARENT`|
|`fio`|string|Обязательный|ФИО или его часть для поиска|
|`limit`|integer|20|Количество элементов (максимум 100)|
|`cursor`|string|null|Курсор следующей страницы|

Поиск регистронезависимый, допускается частичное совпадение ФИО. `fio` — непустая строка до 255 символов, сопоставляется буквально, без шаблонов SQL. `limit` — от 1 до 100.

**Сортировка:**

Лексикографически, по возрастанию:

1. `surname`
    
2. `firstName`
    
3. `patronymic`
    
4. `id`
    

Сравнение ФИО регистронезависимое. `null` в отчестве при сортировке считается пустой строкой.

UUID используется для однозначной сортировки пользователей с одинаковыми ФИО.

### Пример поиска учеников

```
GET /api/v1/directory/users?type=STUDENT&fio=Иванов&limit=20
```

**Пример ответа:**

```
{
  "content": [
    {
      "id": "a550d9c4-5d78-4c4e-85bb-c77950e5c2d2",
      "firstName": "Иван",
      "surname": "Иванов",
      "patronymic": "Александрович",
      "blocked": false,
      "roles": ["STUDENT"],
      "grade": 5,
      "parents": [
        {
          "id": "b550d9c4-5d78-4c4e-85bb-c77950e5c2d2",
          "firstName": "Мария",
          "surname": "Иванова",
          "patronymic": "Петровна"
        }
      ]
    }
  ],
  "limit": 20,
  "hasNext": true,
  "nextCursor": "eyJ2IjoxLC..."
}
```

### Пример поиска родителей

```
GET /api/v1/directory/users?type=PARENT&fio=Иванова&limit=20
```

**Пример ответа:**

```
{
  "content": [
    {
      "id": "b550d9c4-5d78-4c4e-85bb-c77950e5c2d2",
      "firstName": "Мария",
      "surname": "Иванова",
      "patronymic": "Петровна",
      "blocked": false,
      "roles": ["PARENT"],
      "grade": null,
      "parents": []
    }
  ],
  "limit": 20,
  "hasNext": false,
  "nextCursor": null
}
```

### Получение следующей страницы

Клиент передаёт `nextCursor` из предыдущего ответа:

```
GET /api/v1/directory/users?type=STUDENT&fio=Иванов&limit=20&cursor=eyJ2IjoxLC...
```

Сервер возвращает следующие элементы после позиции, указанной в курсоре.

**Правила:**

- Курсор содержит информацию о последнем возвращённом пользователе и является непрозрачной строкой для клиента.
    
- Курсор должен использоваться с теми же фильтрами `type` и `fio`, с которыми он был выдан.
    
- Если следующей страницы нет, `hasNext = false`, `nextCursor = null`.
    
- Если пользователей не найдено, возвращается пустой массив `content`.
    
- Общее количество пользователей и страниц не возвращается.
    
- При поиске учеников дополнительно возвращается список их родителей.
    
- Карточки родителей содержат ID, ФИО, блокировку и роли; `grade = null`, `parents = []`. Вложенные родители в карточке ученика содержат только ID и ФИО.
    
- Логины, пароли и остальные персональные данные в результат поиска не включаются.
    
- Доступ к поиску предоставляется авторизованным преподавателям и администраторам.
    

**Ошибки:**

- `400 Bad Request` — некорректные параметры поиска или курсор.
    
- `401 Unauthorized` — пользователь не авторизован.
    
- `403 Forbidden` — недостаточно прав для поиска.

## 6. Администрирование пользователей

### 6.1. Изменение статуса блокировки пользователя

**Метод:** `PATCH`  
**Endpoint:** `/admin/users/{id}/status`

Администратор блокирует или разблокирует аккаунт пользователя.

Доступ: `ADMIN`. Требуется CSRF. Поле `blocked` обязательно и не может быть `null`.
Повторная установка того же статуса допустима. Ответ: `200 OK` без тела,
с `Cache-Control: no-store`.

Блокировка запрещает вход и обновление токенов, а также защищённые операции
identity-service с уже выданным JWT. Разблокировка восстанавливает доступ.
JWT не отзывается криптографически; другим сервисам нужна собственная проверка блокировки.

**Тело запроса:**

```json
{
  "blocked": true
}
```

Чтобы разблокировать пользователя, передать `"blocked": false`.

**Коды ответа:**
- `200 OK` — статус изменён.
- `400 Bad Request` — некорректное значение статуса.
- `401 Unauthorized` — пользователь не авторизован.
- `403 Forbidden` — нет роли администратора.
- `404 Not Found` — пользователь не найден.

## Открытые вопросы перед реализацией

- HTTP-статусы входа: в реализации используются `200`/`401`; исходный черновик предусматривал `201`/`400`.
- Формат и идемпотентность приглашений зафиксированы в разделе 3.2.
- Ответы и пагинация заявок и поиска дополнены в разделах 4 и 5.
- Правила доступа конкретного преподавателя требуют отдельной связи в модели; сейчас используется общая очередь `PENDING`.
- Привязка второго родителя к существующему ребёнку требует отдельной процедуры подтверждения; текущие ручки создают новый аккаунт.
